# Tech Debt & Deferred Items (v0.1.0 -> v0.12.0)

This document catalogs all accepted design decisions, deferred requirements, known architectural limitations, and test coverage gaps across milestones v0.1.0 through v0.12.0. It serves as the canonical record of trade-offs so that future work does not need to re-discover decisions made during earlier milestones.

## Accepted Design Decisions

These are intentional trade-offs made during v0.1.0 development. Each was the best available option given constraints at the time.

### 1. ✅ Sidecar file persistence instead of SQL-based catalog writes

- **Origin:** Phase 2, decision [02-04] sidecar-persistence
- **Decision:** DuckDB holds execution locks during scalar `invoke()`, which prevents any SQL execution from within DDL functions (`define_semantic_view`, `drop_semantic_view`). Both `try_clone()` (same-instance locks) and `Connection::open(path)` (file-level lock) deadlock or block. The extension writes catalog changes to a `.semantic_views` sidecar file using plain file I/O with atomic rename (write-to-tmp-then-rename). On next extension load, `init_catalog` reads the sidecar and syncs definitions into the `semantic_layer._definitions` DuckDB table.
- **Action:** Resolved. The sidecar file was eliminated in v0.2.0; the v0.2-era `persist_conn` (`pragma_query_t` write-first pattern) was itself superseded in v0.8.0 by the `parser_override` design, which rewrites catalog writes to native DML that runs on the caller's own connection (`persist_conn` no longer exists). A no-op C++ shim was removed in v0.4.0, and a **new** C++ shim was reintroduced in v0.5.0 for the parser-override hook + read-side Catalog-API table functions — persistence itself is pure-Rust native SQL, but "no C++ shim exists" is no longer true.

### 2. ✅ Catalog table naming: `semantic_layer._definitions`

- **Origin:** Phase 2 audit item (catalog table name deviation)
- **Decision:** REQUIREMENTS.md originally specified `_semantic_views_catalog` as the table name. The implementation uses `semantic_layer._definitions` (a dedicated schema with a prefixed table name). This provides better namespace isolation and follows DuckDB conventions for extension-owned objects. The requirement text (DDL-05) was updated to match the implementation.
- **Action:** None needed. The naming is accepted as correct.

### 3. ✅ All output columns are VARCHAR — RESOLVED

- **Origin:** Phase 4, decision [04-03] varchar-output-columns
- **Decision:** Originally declared all columns as VARCHAR to avoid type mismatch panics. Resolved in v0.2.0 with typed output, then further simplified post-v0.2.0 with zero-copy vector references (`duckdb_vector_reference_vector`). Type mismatches are now handled at SQL generation time via `build_execution_sql` casts.
- **Action:** None needed. Output is fully typed with zero-copy transfer.

### 4. ✅ Manual FFI entrypoint instead of macro

- **Origin:** Phase 4, decision [04-01] manual-ffi-entrypoint
- **Decision:** The extension uses a hand-written FFI entrypoint (`src/lib.rs`, mirroring what `#[duckdb_entrypoint_c_api]` generates) rather than the macro, so it can capture the raw `duckdb_database` handle. The handle is used to register the parser-override hook and the read-side/query table functions via the C++ Catalog API.
- **Note (rationale updated):** The original entry justified the manual entrypoint by "creating an independent `duckdb_connection` for `semantic_query()`." That is no longer how queries run: since Phase 65 `semantic_view()` (and the read-side TFs) execute on a **fresh per-call `Connection(*context.db)` opened inside the C++ bind callback**, not a long-lived independent connection. The extension/runtime path opens no independent connection via `duckdb_connect` (the only `duckdb_connect` call in `src/` is in the `#[cfg(not(feature = "extension"))]` unit-test helper `test_helpers::RawDb`, which never runs in the loaded extension). The manual entrypoint is retained for the database-handle capture the registration path needs.
- **Action:** None needed.

### 5. ❌ Native EXPLAIN deferred to v0.2.0

- **Origin:** Phase 4, QUERY-04 (reworded); tracked as QUERY-V2-03
- **Decision:** The `explain_semantic_view()` table function provides expanded SQL inspection as a workaround. Native `EXPLAIN FROM semantic_query(...)` would show the expanded SQL instead of the DuckDB physical plan, but this would require intercepting the EXPLAIN hook, which is not accessible from a loadable extension (Python DuckDB uses `-fvisibility=hidden`).
- **Action:** The C++ shim was removed in v0.4.0 (it was a no-op stub). Native EXPLAIN interception remains architecturally blocked -- it would require DuckDB to expose EXPLAIN hooks via the C API or extension loading mechanism.

### 6. ✅ ON-clause substring matching for join dependency detection — RESOLVED in v0.5.2

- **Origin:** Phase 3, decision [03-02] on-clause-substring-matching
- **Decision:** Transitive join dependency detection originally checked whether a table name appears as a substring in the ON clause of other joins.
- **Resolution:** v0.5.2 Phase 26 replaced this with graph-based PK/FK join resolution (`src/graph.rs`). `RelationshipGraph` uses an adjacency list with reverse edges, Kahn's algorithm for topological sort, and `synthesize_on_clause()` to generate ON clauses from declared PK/FK columns. Phase 27 deleted the legacy `resolve_joins` code entirely — PK/FK graph resolution is now the only join path.
- **Action:** None needed.

### 7. ✅ Unqualified column names required in expressions — RESOLVED in v0.5.2

- **Origin:** Phase 4, decision [04-03] unqualified-join-expressions
- **Decision:** Dimension and metric expressions originally required unqualified column names because the CTE-based expansion flattened all source tables into a single `_base` namespace.
- **Resolution:** v0.5.2 Phase 27 replaced CTE flattening with direct `FROM base AS alias LEFT JOIN ...` expansion. Dimension/metric expressions now use qualified column references (`alias.column`) which resolve correctly against the aliased tables. The `_base` CTE was removed entirely (CLN-02).
- **Action:** None needed.

### 8. ✅ Statement rewrite approach for native DDL — RESOLVED in v0.5.2

- **Origin:** v0.5.0 Phase 16-17, parser extension spike
- **Decision:** Native DDL (`CREATE SEMANTIC VIEW name (...)`) was originally implemented as syntactic sugar over function-call syntax (`:=` named parameters with struct/list literals).
- **Resolution:** v0.5.2 Phase 25 ("SQL Body Parser") implemented a full SQL keyword body parser (`src/body_parser.rs`) that accepts conventional SQL syntax: `TABLES (...) RELATIONSHIPS (...) DIMENSIONS (...) METRICS (...)`. The translation layer in `src/parse.rs` (`rewrite_ddl_keyword_body()`) converts the parsed SQL body into the underlying function-based execution model. No `:=` parameters or struct literals required — pure SQL DDL grammar.
- **Action:** None needed.

### 9. ✅ DDL connection isolation pattern — SUPERSEDED (historical)

- **Origin:** v0.5.0 Phase 17, DDL execution
- **Decision (historical):** The v0.5-era plan_function executed rewritten DDL SQL on a separate `duckdb_connection` created at extension init time and stored as a file-scope static (`sv_ddl_conn`) in `shim.cpp`, to avoid deadlocking the main connection's ClientContext lock held during the bind phase.
- **Superseded:** This mechanism no longer exists — `sv_ddl_conn` has zero occurrences in the codebase. Since v0.8.0 (the `parser_override` unification), write-side DDL is rewritten to **native DML that runs on the caller's own connection**, so it participates in the caller's transaction (the ADBC `autocommit = false` fix). See the accurate entries #23 and #27 for the current DROP/ALTER/CREATE concurrency semantics, and `src/parse/native_sql.rs` for the rewrite. No separate DDL connection is used or needed.

### 10. ✅ Amalgamation compilation via cc crate

- **Origin:** v0.5.0 Phase 15, C++ shim infrastructure
- **Decision:** `duckdb.cpp` (the DuckDB amalgamation, ~23MB / ~300K lines) is compiled alongside `shim.cpp` via the `cc` crate. First build takes ~2.5 minutes; cached on subsequent builds. This provides ALL DuckDB C++ symbols (constructors, RTTI, vtables) without manual stubs. Symbol visibility restricts exports to the entry point only, preventing ODR conflicts with the host DuckDB process. The amalgamation must be version-pinned to match `TARGET_DUCKDB_VERSION`.
- **Action:** The compilation cost is one-time per clean build. `build.rs` feature-gates the C++ compilation behind `CARGO_FEATURE_EXTENSION`, so `cargo test` (default features) is unaffected.
- **Update (DuckDB 2.0 epic, Phase 2):** Superseded. DuckDB 2.0 ships no amalgamation, so `scripts/ensure_engine.py` builds the engine's `duckdb_static` library with DuckDB's own CMake (from the PyPI sdist, or from a harness's `./duckdb` tree), caches it under `.engine/`, and `build.rs` links it and compiles the shim against the engine's full headers (`cpp/engine.manifest`). The visibility restriction is unchanged. See MAINTAINER.md, "The DuckDB engine build".

### 11. ✅ C_STRUCT_UNSTABLE ABI (evaluated, kept; replaced by pinned C_STRUCT for DuckDB 2.0)

- **Origin:** v0.5.0 Phase 18, ABI evaluation
- **Decision:** Evaluated switching from `C_STRUCT_UNSTABLE` to `CPP` ABI for community extension registry compatibility. Rejected: CPP entry point failed in Phase 15 because `ExtensionLoader` referenced non-inlined C++ symbols unavailable under Python DuckDB's `-fvisibility=hidden`. `C_STRUCT_UNSTABLE` pins the binary to an exact DuckDB version (same as CPP in practice). Compatible with the community extension registry (`rusty_quack` uses the same approach). The version-pinning cost is mitigated by the DuckDB Version Monitor CI workflow.
- **Action:** Superseded by the update below: DuckDB 2.0 forced the re-evaluation, and the extension now declares `C_STRUCT`.
- **Update (DuckDB 2.0 epic, Phase 2):** DuckDB 2.0 loads a `C_STRUCT_UNSTABLE` extension only through a new `<name>_init_c_api_v2` entry point, so the extension now declares `C_STRUCT` pinned to the v1.5.6 C API, which 2.0 loads through the existing entry point. `C_STRUCT` drops DuckDB's exact-version check, which the shim still needs (it reads host objects by layout; a v1.5.6 build segfaulted a 2.0 host on `LOAD`), so the entry point now makes that check itself before calling into the shim: `src/load_guard.rs`, guarded by `just test-load-version-guard`. Like the old check, it compares version strings and not source ids.

### 12. ✅ DDL pipeline uses all-VARCHAR result forwarding — SUPERSEDED (historical)

- **Origin:** v0.5.1 Phase 20, C++ result forwarding for DESCRIBE/SHOW
- **Decision (historical):** The v0.5-era DDL parser hook pipeline (`sv_ddl_bind`/`sv_ddl_execute` executing on `sv_ddl_conn`) read results via `duckdb_value_varchar` into `vector<vector<string>>` and declared all output columns as VARCHAR.
- **Superseded:** That pipeline no longer exists — `sv_ddl_bind`, `sv_ddl_execute`, and `sv_ddl_conn` have zero occurrences in `shim.cpp`. Since Phase 65 the read-side table functions (DESCRIBE / SHOW / GET_DDL / READ_YAML) are real C++ Catalog-API table functions whose Rust dispatchers assemble rows and serialize them over the AR-3 self-describing wire format (`src/ddl/read_ffi.rs`). DESCRIBE still declares a deliberate 5-column VARCHAR schema (`object_kind, object_name, parent_entity, property, property_value`) — that is the intended Snowflake-shaped property table, not the retired forwarding pipeline. No further action.

## Known Architectural Limitations

Constraints inherent to the current approach that affect users or maintainers.

### 1. ❓ FFI execution layer not fuzz-covered

- **What:** The `execute_sql_raw` function and `duckdb_vector_reference_vector` call in `src/query/table_function.rs` contain the remaining unsafe code in the extension. The query pipeline uses zero-copy vector references to stream result chunks directly into output, replacing the previous binary-read dispatch.
- **Why:** These functions require the DuckDB loadable-extension function-pointer stubs, which are only initialized at runtime when DuckDB loads the extension via `LOAD`. They cannot run in a standalone test binary.
- **Impact:** The unsafe surface area is significantly smaller than v0.2.0's binary-read dispatch — only `execute_sql_raw` (query execution) and `duckdb_vector_reference_vector` (shared vector ownership) remain in the hot path. Type mismatches are handled at SQL generation time via `build_execution_sql` casts, not at read/write time.
- **Mitigation:** SQLLogicTest integration tests exercise these paths with real data. `tests/vector_reference_test.rs` validates the zero-copy mechanism directly (lifetime safety, multi-chunk, complex types). The 36 PBTs in `tests/output_proptest.rs` still validate end-to-end type correctness via `test_helpers`.

### 2. ❓ DuckDB version pinning (exact)

- **What:** The `duckdb` / `libduckdb-sys` crate dependencies are pinned to an exact version in `Cargo.toml` — the duckdb-rs release tracking the DuckDB version held in `.duckdb-version` (the repo's single source of truth). The encoding is `vX.Y.Z` → `= 1.1XY0Z.0`; `tests::duckdb_version_pins_agree` asserts the two agree, so this entry deliberately does not restate the number.
- **Why:** DuckDB's ABI is not stable across minor versions. An extension built against one version may crash or fail to load with a different DuckDB runtime.
- **Impact:** Every DuckDB release requires a version bump, rebuild, and re-test of the extension. The `DuckDBVersionMonitor.yml` CI workflow automates detection and opens a PR when a new DuckDB version is available.
- **Mitigation:** The version monitor workflow (Phase 1, INFRA-03) detects new releases and opens a PR with `@copilot` mention for automated investigation. Manual version bumps follow the process documented in MAINTAINER.md.

### 3. ✅ All output columns are VARCHAR — RESOLVED

- **What:** Originally, the `semantic_query()` table function returned all columns as VARCHAR. This was resolved in v0.2.0 with binary-read dispatch, then further improved post-v0.2.0 with zero-copy vector references.
- **Current state:** Output columns are fully typed. The table function uses `duckdb_vector_reference_vector` to stream result chunks directly into output with zero copying. Type mismatches between bind-time inference and runtime (e.g., HUGEINT→BIGINT from optimizer changes, STRUCT/MAP→VARCHAR) are handled by `build_execution_sql`, which wraps the expanded SQL with explicit casts where needed.
- **Impact:** None — consumers receive correctly typed output. No manual casting required.

### 4. ✅ Unqualified column names required in expressions — RESOLVED in v0.5.2

- **What:** Dimension and metric SQL expressions originally required unqualified column names due to CTE-based `_base` flattening.
- **Resolution:** See Accepted Decision 7. v0.5.2 Phase 27 replaced CTE flattening with direct `FROM base AS alias LEFT JOIN ...` expansion. Qualified column references (`alias.column`) now work correctly.

Areas where test coverage is reduced compared to ideal, with justification.

### 1. ❓ Iceberg integration test uses Python instead of SQLLogicTest

- **Origin:** Phase 4 audit item; decision [04-03] python-ducklake-test
- **Reason:** The DuckDB SQLLogicTest runner cannot dynamically install extensions (DuckLake, httpfs). The integration test requires loading these extensions to create Iceberg-backed tables.
- **Mitigation:** `test/integration/test_ducklake.py` covers the same semantic query functionality against DuckLake tables. It is run via `just test-ducklake` (local) / `just test-ducklake-ci` (synthetic-data CI variant) and exercises the full round-trip: define semantic view, query with dimensions and metrics, assert correct results.

### 2. ❓ FFI execution layer not fuzz-testable standalone

- **Origin:** Phase 5 audit item (TEST-05 partial scope)
- **Reason:** The loadable-extension function-pointer stubs (`duckdb_query`, `duckdb_value_varchar`, etc.) are only available at runtime when DuckDB loads the extension. A standalone fuzz binary cannot initialize these stubs.
- **Mitigation:** Nine fuzz targets cover the non-FFI attack surface: `fuzz_json_parse`, `fuzz_yaml_parse`, `fuzz_ddl_parse`, `fuzz_keyword_body`, `fuzz_sql_expand`, `fuzz_query_names`, `fuzz_render_roundtrip`, `fuzz_parser_override_ffi`, and `fuzz_where_predicate` (see `fuzz/fuzz_targets/`). SQLLogicTest provides integration coverage of the FFI layer. Post-v0.2.0, the FFI unsafe surface is much smaller — the zero-copy vector reference approach eliminated all per-type binary read/write code; only `execute_sql_raw` and `duckdb_vector_reference_vector` remain in the hot path. `tests/vector_reference_test.rs` validates zero-copy lifetime safety under `cargo test`.

### 3. ✅ Sandbox test portability (resolved in Phase 6)

- **Origin:** Phase 3 audit item (3 catalog sidecar tests failed in sandbox)
- **Reason:** Three Rust tests creating temporary files used hardcoded paths that were inaccessible in sandboxed environments.
- **Resolution:** Phase 6 (decision [06-01] temp-dir-pattern) updated all tests to use `std::env::temp_dir()` for portable temporary file paths. This gap is now closed.

### 4. ✅ DDL prefix whitespace — RESOLVED in Phase 25.1

- **Origin:** Phase 25 proptest surfaced this
- **Resolution:** Phase 25.1 replaced `starts_with_ci` literal prefix matching with
  `match_keyword_prefix` token-based scanning. Every DDL prefix form (the
  `DdlKind` set has since grown to ~15: CREATE / OR REPLACE / IF NOT EXISTS,
  DROP / IF EXISTS, ALTER / IF EXISTS, DESCRIBE, SHOW SEMANTIC
  VIEWS/TERSE/DIMENSIONS/METRICS/FACTS/MATERIALIZATIONS, SHOW COLUMNS) now
  tolerates arbitrary ASCII whitespace (space, tab, newline, carriage return,
  vertical tab, form feed) between keywords. The `prefix_len()` static function
  was replaced by the dynamic byte count returned by `detect_ddl_prefix(query)`.
- **Scope:** ASCII whitespace only (6 characters: 0x09, 0x0A, 0x0B, 0x0C, 0x0D, 0x20).
  Unicode whitespace is handled by DuckDB before the hook fires.

## v0.8.0 additions

### 19. ❓ Read-side table functions see committed state / the primary catalog, not the caller's transaction

- **Origin:** v0.8.0 known limitation; blocker re-evaluated at v0.10.x (AR-6, code-review 2026-07-02).
- **Decision:** The read-side table functions (`describe_semantic_view`, `list_semantic_views`, `show_semantic_*`, `read_yaml_from_semantic_view`, `get_ddl`, and `semantic_view()` itself) read `semantic_layer._definitions` on a **fresh `Connection(*context.db)`** opened inside each C++ bind callback (`cpp/src/shim.cpp`), not on the caller's connection. A fresh connection runs its own transaction, so reads (a) see only **committed** state — a `BEGIN; CREATE SEMANTIC VIEW v ...; SHOW SEMANTIC VIEWS` will not list `v` until the COMMIT lands (**FF-2**), and (b) resolve against the primary/default catalog, ignoring `USE <attached_db>` (the read side of the single-catalog limitation, **TECH-DEBT #26**). Both share this one root cause. Documented for users in CHANGELOG since v0.8.0 and on the transactional-DDL explanation page.
- **Why not the caller's context (AR-6 re-evaluation — corrects the original entry):** The v0.8.0-era note blamed the C API for not exposing `BindInfo`'s connection. That was stale and only half the story. The Phase 65 C++ Catalog-API binds now have the caller's `ClientContext &` in hand, and reads **still** cannot run on it: `ClientContext::context_lock` is a **non-recursive `std::mutex`** the caller holds continuously from parse → bind → exec of the outer query, so the bind callback runs *inside* that held lock. Any re-entrant `context.Query(...)` re-acquires the same mutex and **self-deadlocks** — deterministic, within ~milliseconds, empirically proven by the Phase 65 spikes (`A2-DEADLOCK` at plan time, `EXEC-TIME-RC1` at exec time; the bind phase sits inside the identical held lock; the fresh-connection path is the one that works, `READ-BIND-RC0`). Opening a fresh connection is safe because it takes `connections_lock` (free), not `context_lock`. So exposing the caller's context is **necessary but not sufficient**: no single DuckDB v1.5.4 mechanism provides both liveness and the caller's transaction for a catalog read from inside a bind.
- **Action if DuckDB ever provides both primitives:** Route reads onto the caller's transaction only once upstream provides **both** (a) `ClientContext` / `DatabaseInstance` access through duckdb-rs `BindInfo`, **and** (b) a recursive / relinquishable `context_lock` (or a re-dispatch path that runs the read through the caller's own binder without re-entering `ClientContext::Query`). Note this is not a pure API-surface change: (a) alone is insufficient, because the `context_lock` self-deadlock (b) is the binding constraint. With both, reads move onto the caller's transaction, fixing FF-2 and the read side of #26 together and letting the fresh per-call connection be dropped. Until then this is an accepted limitation grounded in a DuckDB liveness constraint, not an incidental FFI gap.
- **The caller's *session config* is blocked by a SECOND, different wall — do not read this entry as "the only obstacle is `context_lock`" (added 2026-08-02, schema-scoping investigation).** Everything above concerns *executing a query* on the caller's context. Reading a plain **field** off `ClientContext` takes no lock at all and is therefore not subject to the deadlock — so "can the bind see the caller's `search_path` / current schema?" looks like it should be answerable even today. It is not, for an unrelated reason: this project builds against the DuckDB **amalgamation**, and the search path lives in `ClientContext::client_data`, whose type `struct ClientData` is only **forward-declared** there (`cpp/include/duckdb.hpp`), so it has no accessible members. `ClientContext::config` is a by-value `ClientConfig` that *is* defined but carries nothing schema-related, and `ClientContext`'s public API (`Query` / `PendingQuery` / `Prepare` / `TableInfo` / `Append`) exposes no search-path accessor. The only routes past it are building against full DuckDB headers instead of the amalgamation, or hand-declaring the struct layout and reaching in — ABI-fragile UB. Neither is acceptable.
  - **Consequence for schema-scoped resolution:** the read-side table functions cannot resolve an unqualified semantic-view name against the caller's schema on their own. Resolution is therefore threaded in **at rewrite time** — the parser override embeds the caller's search path, which DuckDB evaluates on the caller's connection before the table function is bound.
  - **The injection landed 2026-08-03** (`src/parse/search_path.rs`). Every resolving read table function gained a `search_path` named parameter (`LIST(VARCHAR)`), and the parser override appends `search_path := list_concat(current_schemas(false), [current_schema()])` to each call it sees. What makes this work is that **DuckDB constant-folds table-function arguments on the caller's connection, before the bind callback runs** — so an ordinary scalar expression is the one channel into a bind that the two walls above do not close. (A subquery is not: `Table function cannot contain subqueries`.) `current_schemas(true)` is deliberately not used — it prepends the *temp* schema, itself named `main`, which would win over a real schema of that name.
    - **Not covered: the two scalar functions.** `get_ddl` and `read_yaml_from_semantic_view` are scalars, which have no named parameters, so giving them the path needs a second registered arity. They keep the no-path fallback — the unique match, else an ambiguity error — which is conservative rather than wrong. Recorded under #25.
  - **Update (DuckDB 2.0 epic, Phase 2): the header wall is gone.** The shim now compiles against the engine's full headers, which define `ClientData` (`duckdb/main/client_data.hpp`, with `catalog_search_path`), so a bind could read the caller's search path off its `ClientContext` without a query and so without the `context_lock` deadlock. The rewrite-time injection is kept for now: it works, it is covered, and replacing it changes how every resolving read function binds, which belongs in its own change with its own tests, not in the engine port. Doing so would also give the two scalar functions (`get_ddl`, `read_yaml_from_semantic_view`) the caller's path, closing the #25 gap. The `context_lock` wall above is unaffected and still blocks reading on the caller's transaction.
  - **That injection is forward-compatible and should be deleted when this entry resolves.** The action above would fix the session-config problem incidentally: once reads run on the caller's context, `current_schemas()` inside the catalog query simply evaluates in the caller's session and the injected argument becomes redundant. So the two are the *same* upstream ask, not separate ones — but the injection is what makes DuckDB-conventional resolution possible in the meantime.

### 20. ✅ Bounded LRU evictions are silent at the parser-override site

**Resolved in Phase 62 (v0.8.0), simplified further in Phase 65 / AR-7.** The bounded LRU is gone: multi-DB processes can load the extension into arbitrarily many DuckDB instances without eviction. The Phase-62 design held a per-DB `OverrideContext` (with an intentionally-leaked `duckdb_connection`), but Phase 65 Plan 06's H1 emptied that struct and **AR-7 removed it entirely** — `SemanticViewsParserInfo` is now an empty marker struct (`cpp/src/shim.cpp`), the parser hook carries no per-DB Rust state, and the read side uses a fresh per-call `Connection(*context.db)` instead of any long-lived/leaked connection. So there is no longer any per-DB context to evict *or* leak.

**Original limitation (preserved for archaeology):**

- **Origin:** v0.8.0 B3 (bounded LRU for `parser_override_catalog`).
- **Decision:** The per-extension-load `db_token` → `CatalogReader` map is a 16-entry LRU. A long-lived process that opens more than 16 DuckDB instances will see the oldest token evicted on the 17th load. The next CREATE / DROP / ALTER routed to that token surfaces the friendly error `semantic_views: catalog context for this database has been evicted (process has opened more than 16 databases)`. The eviction itself happens silently inside `parser_override_catalog::set` — there is no log line at the moment of eviction.
- **Why this is acceptable:** The 16-database threshold covers every realistic interactive and CI workload. Daemon processes that load against many databases are the only affected scenario and they get a clear actionable error when they hit the wall.
- **Action if the wall starts to bite:** Either bump the capacity (no other code change needed) or replace the LRU with an explicit registration lifecycle tied to extension-unload (DuckDB does not currently expose an unload hook that we can hook into).

### 21. ✅ `CALL disable_peg_parser()` resets `allow_parser_override_extension` — OBSOLETE 2026-10-16 (DuckDB 2.0 removed the PEG toggles)

> **2026-10-16.** DuckDB 2.0 made the PEG parser the only parser and removed `enable_peg_parser()` / `disable_peg_parser()`, so nothing resets the setting behind the caller's back any more. A session can still set `allow_parser_override_extension` back to `DEFAULT` itself, which turns semantic-view DDL off until it sets `FALLBACK` again; `peg_compat.test` section 4 now pins that. The original entry follows.


- **Origin:** v0.8.0 milestone close, surfaced by `peg_compat.test`.
- **Decision:** DuckDB's `disable_peg_parser` pragma resets `allow_parser_override_extension` to its `default` value (`DEFAULT_OVERRIDE`), which silently bypasses our hook entirely. Subsequent semantic DDL on that connection produces the default parser's `Parser Error: syntax error at or near "SEMANTIC"`. Working around this requires the caller to explicitly re-set `allow_parser_override_extension='FALLBACK'` after disabling PEG.
- **Why deferred:** `disable_peg_parser` is a built-in pragma; parser_override does not see it. The cleanest fix would be a DuckDB-side change so that disabling PEG preserves whatever parser_override setting was in effect.
- **Mitigation:** `peg_compat.test` includes the `SET` workaround and CHANGELOG / MAINTAINER document the gotcha.

### 22. ✅ FALLBACK_OVERRIDE silently drops `DISPLAY_EXTENSION_ERROR`

**Resolved in Phase 62 (v0.8.0).** `parse_function` was re-introduced purely as the error-reporting layer. `parser_override` now defers all validation errors with `DISPLAY_ORIGINAL_ERROR` (rc=2); the default parser fails on the unrecognised DDL prefix; DuckDB calls our `sv_parse_stub`; we re-run validation and return `DISPLAY_EXTENSION_ERROR` with `error_location` set to the byte offset of the offending token. `ParserException::SyntaxError` renders `LINE 1: ... ^` for free. The synthesised `SELECT error('...')` workaround (`sql_throwing`) has been deleted. See `.planning/phases/62-caret-restoration-lru-removal/62-RESEARCH.md` §Q1 (position-tracking contract) and §6 rows B1–B7 for the per-DDL caret coverage.

**Original limitation (preserved for archaeology):**

- **Origin:** v0.8.0 milestone close, surfaced when investigating the post-unification sqllogictest failures (see `sql_throwing` helper in `src/parse.rs`).
- **Decision:** DuckDB's `ParseInternal` (verified in the v1.5.2 amalgamation) ignores any `parser_override` result that isn't `PARSE_SUCCESSFUL` when `allow_parser_override_extension` is `FALLBACK`. That means a Rust-side validation error returned via `DISPLAY_EXTENSION_ERROR` (rc=1 on the FFI boundary) is dropped, and the user sees the default parser's syntax error instead of our message. We work around this by synthesising a `SELECT error('<msg>')` statement and returning it as `PARSE_SUCCESSFUL`, so DuckDB raises the message at execution time. The rc=1 path on the FFI boundary is now dead but kept for forward-compat with `STRICT_OVERRIDE`.
- **Why deferred:** Switching to `STRICT_OVERRIDE` would cause every non-semantic SQL statement to round-trip through our hook with `DISPLAY_ORIGINAL_ERROR`, which is fine semantically but slightly costlier. The synthesised-error workaround has zero overhead on success cases and gives identical user experience.
- **Action if DuckDB ever fixes FALLBACK to honour `DISPLAY_EXTENSION_ERROR`:** Replace `sql_throwing` with a direct `write_error_to_buffer` + rc=1 path; one fewer SQL statement to plan.

### 23. ❓ Cross-connection `CREATE IF NOT EXISTS` race surfaces as PK violation

- **Origin:** v0.8.0 PR #29 ultrareview follow-up; surfaced by the new IF NOT EXISTS path in `test/integration/test_concurrent_ddl.py`.
- **Decision:** `CREATE SEMANTIC VIEW IF NOT EXISTS` rewrites to `INSERT OR IGNORE` against `semantic_layer._definitions(name)`. This atomically absorbs duplicates that are visible in the caller's own MVCC snapshot — same-transaction duplicates and any racing committer that landed before the caller's transaction began. It does **not** absorb duplicates from a transaction that committed *after* the caller's snapshot was taken: both connections evaluate INSERT against snapshots in which the row is absent, both attempt the INSERT, and DuckDB's PK constraint raises a write-write conflict on the second commit. The loser sees `Constraint Error: Duplicate key "name: <view>" violates primary key constraint`, the same shape plain `CREATE` produces.
- **Why this is acceptable:** DuckDB's PK enforcement happens at row insert / commit time and is not a hook we can intercept from within `parser_override`. The pragmatic alternatives — application-level retry-on-conflict, a coarse table-level lock, or a serializable isolation upgrade — all sit outside the parser-override SQL path. The current behaviour is no worse than plain `CREATE` and the loser receives a clear, actionable message rather than corrupting data. The in-snapshot silent no-op contract (the case users hit far more often: re-running an idempotent setup script in a single process) is fully preserved.
- **Mitigation for callers writing parallel bootstrap scripts:** wrap the `CREATE IF NOT EXISTS` in a try/except and treat a constraint violation on the target name as success. `test/integration/test_concurrent_ddl.py::test_concurrent_create_if_not_exists_serializes` pins the failure shape so this caller-side workaround stays valid across releases.
- **Action if DuckDB ever exposes a hook to retry-on-conflict from a parser_override callback:** add an automatic retry loop and convert this entry to ✅ resolved.

### 24. ✅ Body parser's TABLES clause splits on whitespace inside quoted source-table names — RESOLVED in Phase 67

- **Origin:** v0.9.0 Phase 64 RESEARCH §Pitfall 5; surfaced as a known limitation during the quoted-identifier fix.
- **Decision:** `parse_single_table_entry` in `src/body_parser.rs` uses a whitespace-based tokenizer to peel off the alias, the `AS`, and the source-table name from each entry in the `TABLES (...)` clause. If a source-table name has whitespace INSIDE a quoted part (e.g. `TABLES (o AS "my db"."schema"."t" PRIMARY KEY (id))`), the tokenizer truncates mid-name and the parse fails. Whitespace inside quoted source-table parts is vanishingly rare — physical-table names almost never contain spaces, and even when they do (`"sales 2024"`), the user had the option of writing them as `"sales_2024"` or aliasing them outside the semantic-views layer. Fixing this requires `src/body_parser.rs` to adopt the `src/ident.rs` `find_identifier_end` helper at multiple parse points, which is non-trivial body-parser surgery for a vanishingly rare case.
- **Action if a user hits this:** Provide an alias in DuckDB itself (e.g. `CREATE VIEW orders_clean AS SELECT * FROM "my db"."schema"."t"`) and reference the alias in the semantic view's `TABLES` clause. If the case becomes common, port `find_identifier_end` into `src/body_parser.rs::parse_single_table_entry` and surrounding helpers.
- **Resolution:** Resolved in Phase 67 Plan 02 (commits `256ae65` body-parser surgery + `5fb2ed4` sqllogictest fixture). `parse_single_table_entry` (now in `src/body_parser/tables.rs`, after the AR-1 split of the former single-file `src/body_parser.rs` into a module directory) consumes the source-table-name slot via dot-separated `find_identifier_end`-driven advancement BEFORE running the `PRIMARY KEY` / `UNIQUE` keyword scan over the post-name slice. The canonical pathological case (`TABLES (o AS "weird PRIMARY KEY name" PRIMARY KEY (id))`) now parses correctly. Regression coverage: Rust unit tests in `src/body_parser/mod.rs::tests::test_parse_single_table_entry_*` + a sqllogictest fixture at `test/sql/phase67_quoted_source_tables.test`. The `src/ident.rs` helper itself was not modified (D-09).

Sound as far as it went, but it assumed the stored side is a canonical name the user either spells right or wrong. ### 26. ❓ Single-catalog write guard does not cover an attached DB that has its own catalog table

- **Origin:** v0.10.x FF-3 (code-review 2026-07-02). Raised in the PR review of the ATTACH single-catalog guard (`src/catalog/writes.rs::managed_catalog_guard_select`).
- **Decision:** Semantic views are single-catalog: `semantic_layer._definitions` lives in the primary database, and every read runs on a fresh per-call connection that resolves against the primary. The FF-3 write guard raises an actionable error when the caller is `USE`-d into a database that has **no** semantic-view catalog while another database does — the common "USE-d into the wrong database" case. It does **not** fire when the attached database the caller is `USE`-d into ALSO has its own `semantic_layer._definitions` (e.g. it was itself bootstrapped as a primary at some point): the write lands in that catalog while the primary-pinned reads never see it (a silent cross-catalog write).
- **Why deferred:** Firing correctly for that sub-case requires knowing which catalog the read binds actually use (the primary/default database). DuckDB exposes no primary/default-database signal on the caller's connection — there is no `current_setting`, no flag in `duckdb_databases()`, only fragile database-oid ordering — so the guard cannot distinguish "current is the managed catalog" from "current is a second catalog that also happens to hold the table" without a false-positive risk on legitimately attaching a second semantic-views database read-only. The robust fix is to thread the caller's `ClientContext`/current catalog into the read binds so reads and writes agree on one catalog — the reader-context work. **AR-6 (§3.7) re-evaluated this and found it blocked by the same DuckDB liveness constraint as FF-2: reads run on a fresh per-call connection because re-entering the caller's `ClientContext::Query` from a bind callback self-deadlocks on the non-recursive `context_lock` (see the updated entry #19 for the full analysis).** So this sub-case cannot be closed without an upstream DuckDB change; managing two independent semantic-view catalogs from one session is unsupported until then.
- **Action if a user hits this:** Manage semantic views from the single database the extension was loaded into; do not `USE` into an attached database that carries its own `semantic_layer._definitions`.
- **Updated 2026-08-02 (schema scoping, #25).** Write DDL that spells out a `<database>.` prefix is now checked against `current_database()` and rejected when it names another database, so `DROP SEMANTIC VIEW otherdb.analytics.v` no longer silently deletes the *current* database's `analytics.v`. That closes the explicitly-written half. **The read side still ignores a database prefix** — `semantic_view('otherdb.analytics.v')` pins the schema but not the database, so it reads the catalog's `analytics.v`. The read binds have no way to compare against the caller's database for the same reason the rest of this entry is deferred (a fresh per-call connection, #19), and the extension manages exactly one catalog anyway, so the reference can only be either redundant or unsupported. Worth closing alongside the reader-context work rather than before it.

### 27. ❓ DROP / ALTER existence guards are snapshot-consistent with their DML only inside an explicit transaction

- **Origin:** v0.10.x FF-1 (code-review 2026-07-02, §3.6). The DROP/ALTER sibling of #23 (which covers only CREATE).
- **Decision:** A non-`IF EXISTS` DROP/ALTER rewrites to a multi-statement string — one or more pure-SQL guard `SELECT`s (`existence_guard_select`, `rename_collision_guard_select`) followed by the `DELETE`/`UPDATE` — that DuckDB re-parses and runs on the caller's connection (`src/parse/native_sql.rs::rewrite_drop`/`rewrite_alter_rename`/`rewrite_alter_comment`; guards in `src/catalog/writes.rs`). Whether the guard's check is consistent with the DML depends on the caller's transaction state, and this was verified empirically: **inside an explicit transaction** (`BEGIN … COMMIT`, or an `autocommit = false` ADBC/PG connection) every emitted statement shares the one snapshot, so the check is atomic with the DML; **under autocommit** (the default) DuckDB commits after *each* statement of a multi-statement string, so the guard and the DML run in separate implicit transactions. A different connection that commits in the window between them can invalidate the guard's decision:
  - concurrent DROP — both existence guards pass, both `DELETE`s run; the loser's `DELETE` matches 0 rows and reports success having deleted nothing (a silent no-op, not an error);
  - concurrent RENAME — the loser's collision guard passes, then the `UPDATE` hits DuckDB's primary-key constraint and surfaces a raw `Constraint Error: Duplicate key` instead of the friendly `already exists` wording (the same failure shape as #23).
- **Why this is acceptable:** The behaviour is no worse than the equivalent native-`CREATE`/`DROP` concurrency (#23) and the far more common single-process case (re-running an idempotent setup script) is fully consistent. Closing the window by emitting our own `BEGIN … COMMIT` around the rewrite is **not** viable: DuckDB rejects a nested `BEGIN` (`TransactionContext Error: cannot start a transaction within a transaction`, verified), so the wrapper would fail outright whenever the caller is already in a transaction, and an emitted `COMMIT` would prematurely commit an `autocommit = false` caller's in-flight work — breaking the transaction-participation contract the native-DML rewrite exists to provide (the v0.8.0 ADBC fix). Folding the guards into a single statement (as `CREATE` does via `CASE … error()` inside the `INSERT`) does not generalise to the DROP/ALTER "must (not) exist" pre-checks, which need to raise on the *absence*/*presence* of a row a single `DELETE`/`UPDATE` cannot key off.
- **Mitigation for callers needing atomic check-and-write:** wrap the DDL in an explicit `BEGIN … COMMIT` (or use a connection with `autocommit = false`). All emitted statements then share one snapshot and the guard is consistent with the DML; a concurrent committer instead triggers a serialization/PK conflict at `COMMIT`, which the caller can retry — the same pattern as #23's `CREATE IF NOT EXISTS` mitigation.
- **Action if DuckDB ever exposes the caller's transaction state (or a retry-on-conflict hook) from a `parser_override` callback:** conditionally wrap the rewrite in `BEGIN … COMMIT` only when the caller is under autocommit, and convert this entry to ✅ resolved.

The private per-check helpers (`check_*`) and the externally-shared sub-validators (`RelationshipGraph::from_definition` / `check_no_diamonds` / `check_no_orphans` / `validate_fk_references` / `toposort`, also called by `SHOW … FOR METRIC`) keep their `String` signatures and are wrapped at the public boundary — so nothing `String`-typed propagates upward past the graph module, and no unrelated caller is disturbed.
- **Why `position` is `None` (the deliberate boundary):** these validators receive a fully-built `SemanticViewDefinition` whose members (`Metric`/`Dimension`/`Fact`/`Join`) hold **owned** names and expressions, not byte spans into the original DDL, and the original query text is out of scope by the time they run — so `util::byte_offset_within` (which needs the offending token to be a *subslice of the original query*) cannot be applied here. Additionally, several of these failures are **global/topological** (a derived-metric or fact dependency cycle, an ambiguous join *diamond*, an empty `TABLES` clause) with no single offending token to point a caret at. This mirrors the already-accepted positionless-typed `expand::ExpandError` (fan-trap) and the pervasive `position: None` idiom at the parse layer's own semantic-failure sites.
- **What real carets here would require (not done — out of proportion):** threading the original DDL body **and** a per-item byte-span table down into `SemanticViewDefinition`'s members (or passing them as a side channel into `enrich_definition_for_create`), then, for the *token-shaped* subset — duplicate name, unknown metric/fact reference, unknown source table, unknown/misrouted USING relationship, self-reference, FK/PK mismatch — recovering the offset with `byte_offset_within`. The global/topological subset stays positionless regardless. A future PR can add spans if define-time carets for these become worth the model change.

### 33. ✅ Struct-domain fuzz targets tested unreachable inputs — oracles corrected (converge-once + fragment precondition + double-quote balance); full redesign considered and declined

- **Origin:** 2026-07-18. Once CI-1 made the fuzz targets actually run, `fuzz_render_roundtrip` and `fuzz_sql_expand` both flagged non-bugs. Both are symptoms of one design flaw: the targets `#[derive(Arbitrary)]` a whole `SemanticViewDefinition`, but `render`/`expand` are only ever called on **parser-produced** structs. The manufactured input domain is far larger than the reachable one, so each oracle has to re-derive "is this input well-formed?" — and that re-derivation is where the false positives live.
  - `fuzz_render_roundtrip`: the strong fixpoint `render(parse(render(def))) == render(def)` is **unsatisfiable** on arbitrary defs — a free-form `expr` with surrounding whitespace is trimmed by the parser (`" "` → `""`) and cannot be quote-protected. (The e35cf15 identifier quote-protection only ever mattered for such unreachable inputs; it is a no-op for parser-produced defs and is kept as defensive hardening.)
  - `fuzz_sql_expand`: `def_fragments_balanced()` (a precondition guarding the `is_balanced` assertion) omitted the `output_type` and window `window_function` fragments, which `expand` interpolates raw into `CAST(expr AS <type>)` / `FUNC(...)`; an unbalanced type/function name then manufactured unbalanced SQL from "balanced" inputs.
- **Applied (A, merged in #135):** `fuzz_render_roundtrip` switched to the **converge-once** invariant — normalize once via `parse(render(def))` to land on a parser-produced def, then assert `render` is idempotent on it (mirrored by the `assert_render_fixpoint` unit helper + three regression tests in `render_ddl.rs`). `fuzz_sql_expand`'s precondition extended to include `output_type` (dim/metric/fact) and `window_function`. `fuzz_query_names`'s paren-balance oracle extended to skip double-quoted identifiers (a fuzzed name emitted as `quote_ident`ed can legally contain a paren — Copilot review). Coverage is preserved: the strict `parse(render(def)) == def` equality for canonical defs lives in `tests/roundtrip_proptest.rs`.
- **Considered and declined (B):** the from-scratch trust-boundary redesign (fuzz raw text/bytes; derive every struct by parsing; differential oracles; libFuzzer-vs-proptest split; curated seed corpus) was evaluated and **not pursued**, because its premises largely do not hold now that the oracles are correct:
  - Its central claim — "derive structs by parsing, so the balance precondition vanishes (a parsed def's fragments are balanced by construction)" — is **false**: `src/body_parser/entries.rs` rejects unterminated quotes and empty exprs but **not** unbalanced-paren exprs, so a parse-derived def can still carry an unbalanced fragment and `fuzz_sql_expand` would *still* need a balance guard.
  - The "does DuckDB accept the expanded SQL?" differential oracle **already exists**: `tests/differential_proptest.rs` executes `expand`'s output against in-memory DuckDB for canonical defs, so structural validity is already covered where it can be meaningfully checked (needs the base tables to exist — a fuzz target avoids DuckDB for speed).
  - Converting the two struct targets to raw-bytes/text fuzzing would **lose coverage** (most random bytes never parse into a full view) for marginal gain. The hand-rolled balance oracles are the right *kind* of check for a fast, DuckDB-free fuzz target; the fix was completing their preconditions, not replacing them.
  - What narrow B landed instead: two targeted `fuzz_keyword_body` seeds at the recently-fixed constructs (a quoted, comma-/paren-bearing constraint column list; a `MATERIALIZATIONS` clause) and this decision record. `Arbitrary`-on-the-struct stays correct for the serde targets (`fuzz_json_parse` / `fuzz_yaml_parse`), which have no sub-grammar. The text-boundary targets (`fuzz_ddl_parse`, `fuzz_keyword_body`) were already well-seeded, and `Fuzz.yml` / the `just fuzz` recipes already pass both `fuzz/corpus/<t>` and `fuzz/seeds/<t>` to libFuzzer, so seed files are used.

### 35. ✅ Fan-trap fix errors on multi-grain queries; per-grain ("own-grain") metric aggregation — the Snowflake-parity real fix — RESOLVED in v0.12.0

- **Origin:** code-review 2026-07-02 §SG-1/6/7/16 (the policy call) and 2026-07-18 §2 / §"design decisions worth documenting" (the root-anchored `FROM` shared root cause of EXP-1/2/3/5). Recorded here so the deferral stops living only in the review notes — it had no TECH-DEBT entry despite being the largest open query-expansion-semantics item.
- **Decision:** the generated query is always anchored `FROM <root table>` with `LEFT JOIN`s outward. A metric whose grain is a parent/ancestor of the root, two metrics (or one derived/window metric) spanning a fan-out edge, or an active semi-additive metric over a fanned join, therefore aggregate over the *multiplied* join. The EXP-1/2/3 work (CHANGELOG `[Unreleased]`; `expand/fan_trap.rs` + the `RootGrainFanTrap` variant) closes the **silent-wrong-answer** half: every such shape now **errors** loudly (`RootGrainFanTrap` / `MetricFanTrap` / the semi-additive fan check), so the project's "error rather than silently inflate" contract holds uniformly. It does **not** make these queries *return* correct numbers.
- **The deferred real fix:** Snowflake computes each metric at its **own grain** — pre-aggregate each metric's source table to its grain in a per-metric CTE, then join the pre-aggregated results — so a parent-table metric alongside a child-table dimension yields the right value instead of erroring. That replaces the single root-anchored `FROM` with per-grain aggregation CTEs and interacts with materialization routing, fan-trap detection, and the semi-additive / window paths, so it was explicitly scoped as a **follow-up milestone**, not part of the correctness-fence work.
- **Why deferred:** erroring is safe (correct-or-nothing) and shippable immediately; the per-grain rewrite touches the core expansion topology and is milestone-sized. Landing the loud error first removed the data-corruption risk without blocking on the larger change.
- **Impact:** a query Snowflake would answer by computing a metric at a coarser grain than the root currently raises a fan-trap error here. Workarounds: query each grain separately, or declare the coarser table as the base.
- **Action:** implement per-grain metric CTEs ("compute each metric at its own grain") as a dedicated milestone; the errored shapes then become answerable and this entry flips to ✅. Until then, the root-anchored `FROM` divergence is worth an explicit statement in the docs/architecture notes (2026-07-18 §2).
- **Resolved (v0.12.0, Phases 69-71):** `src/expand/per_grain.rs` implements the per-grain rewrite. When a base-anchored `FROM` would inflate the query, each metric is aggregated in a CTE anchored at **its own** grain table and the results are joined on the queried dimensions — `FULL OUTER JOIN` with NULL-safe key comparison (a dimension group present at one grain and absent at another survives with a NULL metric), or `CROSS JOIN` when the query has no dimensions. A derived metric spanning grains is decomposed into per-grain component columns and its expression re-evaluated over them. All three shapes this entry named are now answered: the parent/ancestor-grain metric (alone or with dimensions at/above its grain), multi-grain metric combinations (fan and chasm), and the single multi-grain derived metric. `check_fan_traps` gained a per-grain mode that suppresses exactly the two checks per-grain supersedes (metric-grain × root, metric × metric) and keeps the metric × dimension check, which is about a dimension below a metric's grain and is not something per-grain can define. The routing predicate fires only where v0.11.0 errored, so single-grain SQL is byte-identical. The docs statement this entry asked for landed too: `docs/explanation/snowflake-comparison.rst` §"Metric Grain" and `docs/how-to/fan-traps.rst` §"Multi-Grain Queries". Residual gaps are entry #36.

### 36. ✅ Multi-grain queries involving window / role-playing / active semi-additive metrics — RESOLVED in v0.12.0

- **Origin:** v0.12.0 (Phase 69), the residual of entry #35. Recorded separately so #35's resolution is not overstated.
- **Decision:** the per-grain planner (`per_grain::is_eligible`) declines — leaving the v0.11.0 fan-trap error in place — when a queried metric is an *active* semi-additive metric (a `NON ADDITIVE BY` whose snapshot dimension is outside the query) or carries `USING` role-playing context, and when a queried dimension has no source table (an unqualified expression, whose binding would move if the anchor moved). Each of those strategies emits its own base-anchored CTE (`__sv_snapshot`) or needs role context the grain CTEs do not carry; routing them through per-grain emission without designing that interaction would risk exactly the silent-wrong-answer class v0.11.0 closed.
- **Window metrics — RESOLVED:** `per_grain::window_cte_anchor` now picks the grain for an all-window query and `expand_window_metrics` anchors `__sv_agg` there via `push_from_anchor` + `anchor_joins`, instead of `push_from_base`. The window function itself is not grain-sensitive — it runs over the already-grouped CTE — so anchoring the CTE at the **inner** aggregate's own table was the whole fix. The anchor is decided *before* the fan-trap fence and puts it in the same per-grain mode the plan does, which suppresses the two checks the anchor supersedes and keeps the metric × dimension check (a dimension below the metric's grain is still an error, in both engines). The anchor is derived from the inner metric specifically, not from `metric_grain_tables` on the window metric: DDL qualifies a window metric with a source alias, and that helper unions the alias with the inner's for its own conservative purpose, which would report two grains for every DDL-declared window metric.
  - Still declined, deliberately: window metrics whose **inner aggregates sit at different grains** (those grains would have to be joined before the window runs — the next increment), a root-grain inner aggregate (base-anchoring is already correct), role-playing, and unqualified dimensions.
- **Role-playing — NARROWED to a per-query test:** the role-playing gate asked a *definition*-level question ("does any table have two inbound relationships from one source?"), so **every** query against a definition that declared role-playing anywhere lost per-grain emission — including queries whose grains and dimensions never reach the role-played table, whose CTEs join nothing ambiguous and need no role context. It now asks the query-level question via `role_playing_on_path` over the tables the query touches — dimension source tables ∪ `metric_grain_tables` ∪ the `where_clause`'s source tables. The predicate's tables belong in that set because `anchor_joins` chains them into the sources it walks, exactly like a dimension's; omitting them in the first cut let a predicate on a role-played table through, and the grain CTEs then bound it to the first-declared relationship via `edge_between` — a silent wrong answer where the shape had previously raised `MetricFanTrap` (caught in review on PR #176, pinned by `where_clause_reaching_a_role_played_table_declines_per_grain`). Checking the touched tables also covers the joins between them: the relationship graph is a tree apart from the sanctioned role-playing multi-edge, so any node on the path between two touched tables is an ancestor of one of them and the walk to the root passes through it.
- **Role-playing — `USING` now threaded into the grain CTEs:** a co-queried metric's `USING` names which role a dimension on a role-played table means, and `anchor_joins` now emits that hop under its scoped alias (`a__dep`) joined on the NAMED relationship, with `dim_expr` rewriting the dimension's qualifier to match — the same shape the base-anchored path has always produced, so the two agree. `edge_between` is deliberately bypassed for such a hop: it returns whichever of the several edges is declared first, which is the mis-binding the gate exists to keep out of this emitter. `is_eligible`'s blanket "no metric with `USING`" test narrowed to "every relationship its `USING` names is one this path threads", so `USING` on a single-edge relationship (which the base-anchored path scopes itself) still declines rather than being guessed at.
  - Still declined, deliberately, because only a *dimension's* expression is rewritten to the scoped alias: a `where_clause` member on a role-played table, a metric's own grain table on one, and any table reachable only *through* one (`find_using_context` rejects the descendant case outright). The window path stays strict for the same reason — `__sv_agg`'s SELECT list gets no scoped-alias rewrite — and passes an empty role map to `anchor_joins`.
  - Was previously: a query that *does* reach a role-played table. A grain CTE would have to choose among that table's relationship instances, and choosing silently is the declaration-order-dependent mis-binding the fence exists to prevent. Threading `USING` into `anchor_joins` — so a grain CTE joins the *named* role and the dimension is emitted against its scoped alias (`a__dep`) — is the remaining half of this sub-item. The machinery it needs already exists (`role_playing::find_using_context`, `expr_tokens::rewrite_qualifier`, and `ResolvedJoin`'s `scoped` / `emit_alias` fields, which `anchor_joins` currently hardcodes to the bare alias).
- **Impact:** Snowflake answers these; we error. In practice they are the corner where multi-grain meets two features that are themselves uncommon — a single-grain query using either is unaffected.
- **Snowflake behaviour — measured, not inferred (2026-07-31).** The docs state the semi-additive rule ("the rows are sorted by the non-additive dimensions, and the values from the last rows ... are aggregated ... in each group of queried dimensions") and the dimension-grain rule separately, but never their interaction, and every documented semi-additive example is single-table. Probed directly against Snowflake with a two-grain fixture (customers 1 row each; accounts fanned 2-3 per customer, two snapshot dates), querying an *active* semi-additive metric at the account grain together with a plain metric at the customer grain:
  - **Per-grain confirmed.** `customer_count` returned 2/1 — the own-grain answer. A base-anchored plan would have returned 3/1 (customers counted over the rank=1 rows) or 6/2 (over all joined rows); the fixture was built so the three are distinguishable, and each variant was computed in DuckDB beforehand. `total_balance` returned 350/70, the latest-snapshot value, confirming the snapshot rule genuinely fired rather than both dates summing (385/77). So Snowflake computes the snapshot *inside* the metric's own-grain aggregation and joins the pre-aggregated results — the same model per-grain already implements for plain metrics.
  - **An NA dimension may live on ANOTHER table.** A bare `NON ADDITIVE BY (report_date)` naming a dimension declared on a *parent* of the metric's table fails at CREATE with `invalid identifier 'REPORT_DATE'` — bare names resolve in the metric's own logical-table scope — but the **qualified** form `NON ADDITIVE BY (s.report_date)` is accepted and returns the same per-grain answer in a multi-grain query. Our dotted-NA support (#30) is therefore *aligned* with Snowflake, not more permissive.
  - **The dimension-grain fence matches.** Requesting a metric with a finer-grained dimension errors: `The dimension entity 'A' has a higher level of granularity than the base metric entity 'C'. Consider selecting a dimension from an entity that is related to and has a lower level of granularity than 'C'.` (Snowflake's "higher granularity" means *finer*.) That is the rule `fan_trap.rs` already enforces.
- **Consequence for the implementation — a join source the current code does not collect.** An *active* semi-additive metric is by definition one whose NA dimension is **not** queried, so that dimension's table never appears in `resolved_dims` and `per_grain::anchor_joins` will not join it. Combined with the finding above that the NA dim may sit on another table, a grain CTE would emit `RANK() ... ORDER BY s.report_date` against a `FROM` that never binds `s` — the same unbound-alias class as the #177 single-grain defect. `semi_additive::collect_na_dim_source_tables` already computes exactly this set for the base-anchored path; per-grain must feed it into `anchor_joins` alongside the dimension and `where_clause` tables.
- **Increment 1 landed:** `per_grain::snapshot_cte_anchor` re-points `__sv_snapshot` at the metric's own table when every queried metric sits at one non-base grain that the base-anchored join fans, and `semi_additive` emits its FROM/JOINs through `push_from_anchor` + `anchor_joins` in that case. Deliberately the same shape as `window_cte_anchor`, including its direction restriction: only re-anchor onto the "one" side, because for a metric on a CHILD of the base table `FROM base LEFT JOIN child` already yields each child row once and its LEFT JOIN keeps childless parents as NULL-extended rows — flipping the anchor would silently DROP those groups, and this single-CTE path has no FULL OUTER JOIN reassembly to restore them. The NA dims' source tables are passed to `anchor_joins` as extra sources (`semi_additive::na_dim_source_tables`, exposed for the decision `sql_gen` must make *before* the fan-trap fence runs), which is what makes the probed off-table NA dimension bind; without it the re-anchored CTE would emit `ORDER BY d.report_date` over a FROM that never joins `d`.
- **Increment 2 landed — entry closed.** `per_grain` now emits the snapshot as one grain group's CTE, nested as `SELECT <outer> FROM (<inner>)` so the rows are ranked before that grain aggregates them, while sibling groups aggregate normally and the results join as usual. `Group` carries its metrics' canonical names (not just the built expressions) because a snapshot group must decompose the metrics themselves; names rather than `&Metric` keep `Plan` free of a lifetime. `render_snapshot_group` calls the shared `semi_additive::build_snapshot_block`, which numbers its `__sv_semi_{i}` capture columns by position within the metrics it is *given*, so each group gets an independent namespace and two snapshot groups in one query cannot collide.
  - A query whose ONLY group is a snapshot group is deliberately declined by `plan`, leaving it to increment 1's verified single-CTE shape rather than re-routing it through a one-group plan that would emit the same thing inside an extra wrapper.
  - `expand_per_grain` now returns `Result`: `build_snapshot_block` can reject a metric that is not a single bare aggregate (SG-5), and that diagnostic should reach the user rather than be swallowed into a fan-trap error.
  - All four sub-items of this entry are now resolved: window metrics (#175), role-playing eligibility (#176) and `USING` threading (#177), semi-additive own-grain (#179) and multi-grain (this change).

### 38. ✅ `USING` / `NON ADDITIVE BY` written AFTER `AS` were silently swallowed into the metric expression — RESOLVED 2026-08-01

- **Origin:** hit while writing `semi_additive_own_grain.test` during the TECH-DEBT #36 semi-additive work (PR #179); noted in that PR's body and filed here rather than fixed inline, being unrelated to the emitter change.
- **Symptom:** a metric entry with a pre-`AS` clause written in the wrong position is **accepted at CREATE**, its declared semantics silently discarded, and the view is left unqueryable. Both affected clauses, verified against the built extension:

  ```sql
  METRICS (t.m AS sum(t.v) NON ADDITIVE BY (d))   -- CREATE ok, query fails
  METRICS (t.m AS sum(t.v) USING (r))             -- CREATE ok, query fails
  ```

  `DESCRIBE SEMANTIC VIEW` then reports `EXPRESSION = 'sum(t.v) NON ADDITIVE BY (d)'` with **no** `NON_ADDITIVE_BY` property row: the metric is stored as an ordinary additive metric whose expression happens to contain uninterpretable text. `GET_DDL` round-trips that text faithfully, so the malformed definition survives a dump/reload. The failure surfaces only at query time, as a confusing parser error pointing inside generated SQL rather than at the user's DDL:

  ```
  Binder Error: ... type inference failed for query `SELECT sum(t.v) NON ADDITIVE BY (d) AS "m" ...`:
  Parser Error: syntax error at or near "ADDITIVE"
  ```

  The silent discarding is the worse half: a user who mistypes the clause position gets a view that creates cleanly and reports itself as a plain metric, so the semi-additive (or role-scoping) intent is lost with no diagnostic anywhere.
- **Cause:** `body_parser::metrics::parse_metric_entry` parses `USING (...)` and `NON ADDITIVE BY (...)` from the prefix **before** `AS`, then takes everything after the `AS` token as `raw_expr` (`metrics.rs:150`). Text after `AS` is therefore expression by construction, and nothing inspects it for a misplaced clause keyword. `OVER (...)` is not affected — `parse_window_over_clause` runs on `raw_expr`, so a window clause after `AS` is genuinely parsed (confirmed as a control alongside the two cases above).
- **Fixed as sketched.** `parse_single_metric_entry` now scans the post-`AS` text — after trailing annotations and the `OVER` clause have been stripped — for a depth-0 `USING` / `NON ADDITIVE BY` run via the existing quote- and depth-aware `Cursor::find_kw_depth0` / `find_kw_seq_depth0`, and rejects with a message naming the clause and where it belongs. Reuse, not new machinery.
  - Scanning at **depth 0** is what makes it safe: an aggregate call's contents sit at depth >= 1, so a depth-0 keyword can only be OUTSIDE the call — exactly the misplaced position. Quote-awareness covers the other direction: the same words inside a string literal or quoted identifier stay data. `OVER (...)` is unaffected, having already been consumed.
  - **Review follow-up (#181):** the depth-0 scan alone was bypassable by parenthesising the WHOLE expression (`AS (sum(v) USING (r))`), which pushed the keywords to depth 1 — the same bug through another door, silently creating and failing only at query time. `Cursor::is_wholly_parenthesised` now strips redundant outer wrappers before the scan. Deliberately narrow: only a wrapper whose opening bracket matches the LAST token is stripped, so a structural `(...)` keeps its contents nested and a genuinely nested `USING` inside a subquery's JOIN stays legal (guarded both as a unit test and end-to-end). The same review moved the `before_as.is_empty()` check ahead of the scan, so a missing metric name is still reported as such rather than pre-empted by the misplaced-clause error.
  - Both rejections have independently-reporting unit tests in `body_parser::tests`, plus controls in the same module — a legitimate `OVER` after `AS`, and the keywords inside a string literal — so over-rejection would fail as loudly as under-rejection. `misplaced_metric_clause.test` proves it end-to-end at CREATE; its two `statement ok` guards were confirmed to pass with the fix reverted, so they are guards rather than capabilities.
- **Impact:** low severity, low frequency — the query-time error does eventually stop the user, and the correct spelling is what the docs and every example show. It is filed because the failure is *silent at the point of the mistake* and *survives GET_DDL*, which is the shape this project treats as worse than an outright error.

### 39. ✅ Fan-trap fence never checked the `NON ADDITIVE BY` dimension's own table — silent double-count (EXP-9) — RESOLVED 2026-08-03

- **Origin:** code review 2026-08-03 (`_notes/code-review-2026-08-03.md`, EXP-9), reviewing `v0.10.4..HEAD`. Direct descendant of EXP-3 (#—, code review 2026-07-18), which made active semi-additive metrics subject to the fence's metric × dimension and metric × metric checks but did not cover the table the snapshot joins *because of the NA dimension itself*.
- **Symptom:** an ACTIVE semi-additive metric (its `NON ADDITIVE BY` dimension not among the queried dimensions) whose NA dimension sits on a table that fans the metric's grain was aggregated over a join that had already duplicated the metric's rows. `RANK` ties across the fanned duplicates of one source row are indistinguishable from ties across distinct rows, so the snapshot CTE could not dedupe them and the value was added once per duplicate. Wrong number, no error:

  ```sql
  -- orders (base) <- line_items (many side); one order, two line items sharing a ship_ts
  METRICS (o.balance_at NON ADDITIVE BY (ship_ts) AS sum(o.balance))
  semantic_view('v', metrics := ['balance_at'], dimensions := ['region'])  -- returned 200.00 for a 100.00 balance
  ```

  The asymmetry is what makes it unmistakable: *querying* `ship_ts` makes the metric regular, and the fence has always raised `FanTrap` for the identical join. The un-queried case was the permissive one.
- **Cause:** `check_fan_traps`'s metric × dimension loop iterates `resolved_dims` — the *queried* dimensions. An un-queried NA dimension appears there nowhere, while `collect_na_dim_source_tables` joins its table into the snapshot CTE exactly as a queried dimension's table is joined. A metric at the base grain also skips the root-grain loop (`met_table == root`), so nothing checked the join at all. `snapshot_cte_anchor` does not rescue it: it returns `None` when the metric is already at the root grain, and where it *does* re-anchor it checks only that its extra tables are reachable, never that reaching them is non-fanning.
- **Resolution:** `semi_additive::na_dim_fence_members` returns `(metric index, NA dimension name, source table)` for every active NA dimension contributing a bare join — the same entries `collect_na_dim_source_tables` turns into join targets, paired back to the metrics whose rows that join multiplies. `check_fan_traps` runs the existing path/fanning-edge test over them and reports `FanTrap` naming the NA dimension. Role-scoped NA dims are excluded for the same reason they contribute no bare join (T-15). Placed **above** the `per_grain` early return: the join lives inside the snapshot CTE, which the base-anchored and anchored/per-grain emitters both build from the shared `SnapshotBlock`.
- **Coverage:** `expand::tests_fan_trap::{semi_additive_na_dim_on_fanning_table_blocked, semi_additive_na_dim_queried_is_already_blocked, semi_additive_na_dim_on_non_fanning_table_allowed}` (independently reporting, so the controls cannot be masked) and `test/sql/cr20260803_silent_fan_and_role.test` end-to-end with the tie that surfaces the double-count.

### 40. ✅ `where_clause` member on a role-playing table bound to the first-declared relationship (EXP-10) — RESOLVED 2026-08-03

- **Origin:** code review 2026-08-03 (`_notes/code-review-2026-08-03.md`, EXP-10), on the `where_clause` feature added post-v0.12.0. The role-playing seam EXP-4/EXP-5 closed for dimensions and facts, re-opened by a new member-bearing surface.
- **Symptom:** a predicate naming a member on a role-playing table filtered through whichever relationship was declared first, silently. With a co-queried metric's `USING` naming the *other* role, the query grouped by one instance and filtered by the other:

  ```sql
  -- flights -> airports via dep AND arr; metric arr_count USING (arr)
  semantic_view('v', metrics := ['arr_count'], where_clause := 'city = ''NYC''')
  -- emitted: LEFT JOIN airports a ON f.dep_code = a.code
  --          LEFT JOIN airports a__arr ON f.arr_code = a__arr.code
  --          WHERE (a.city) = 'NYC'      <- counting arrivals, filtering departures
  ```
- **Cause:** role-playing ambiguity is checked for queried dimensions (`find_using_context`) and, on the facts path, for queried dimensions and facts (`check_fact_role_playing_path`). A `where_clause` member's table is in neither set: it rides `resolve_joins_pkfk`'s `fact_source_tables` parameter, whose loop — unlike the dimension loop — never consults `role_playing_bare_aliases`, so the bare alias is joined via `tree_parent`, the first-declared edge. The per-grain planner already declined this shape (where-tables are in its "strict" set), but declining routes the query to the base-anchored path, which emitted it silently.
- **Resolution:** `role_playing::check_where_clause_role_playing_path`, the sibling of `check_fact_role_playing_path`, rejects a member whose table is (or is reached only through) a role-playing target via the shared `role_playing_on_path`. Called on both emission paths — beside `check_where_clause_fan_traps` on the metrics path, and as step 3d on the facts path — so it is decided above the per-grain / anchored / base-anchored split. New error `ExpandError::AmbiguousWhereClausePath`.
- **Why not infer the role from a co-queried metric's `USING`:** only a queried *dimension's* expression is rewritten to a scoped alias, so a predicate member has no way to name its role; several co-queried metrics may name several roles, and a predicate is bound to none of them. Picking one would be a guess, and guessing is what produces a wrong number instead of an error — the EXP-4/EXP-5 reasoning.
- **Coverage:** `expand::tests_role_playing::{where_clause_on_role_playing_table_is_rejected, where_clause_role_playing_does_not_filter_through_the_other_role, where_clause_on_non_role_playing_table_still_allowed}` plus `test/sql/cr20260803_silent_fan_and_role.test` (including a control that a `where_clause` on a non-role-playing table still filters pre-aggregation, and that a queried dimension still resolves through `USING`).

### 41. ✅ `where_clause` was pinned to its inert default in every numeric proptest oracle (PBT-6) — RESOLVED 2026-08-04

- **Origin:** code review 2026-08-03 (`_notes/code-review-2026-08-03.md`, PBT-6). All five differential/numeric harnesses in `tests/` pinned `where_clause: None`, so the newest number-changing feature had no randomized coverage on any path — the blind spot EXP-9 (#39) and EXP-10 (#40) reached `main` through.
- **Closed so far (2026-08-03):** `differential_proptest` (base-anchored single-table) and `star_schema_proptest` (per-grain CTEs, plus a new rejection property for a child-side predicate against a parent-grain metric). Both generate a predicate AST rendered twice — member names into the request, raw columns into the oracle — and both declare `LABELS = (FILTER)` members with compound expressions so member substitution and its parenthesization are load-bearing rather than identity. Each carries a generator-coverage guard asserting the parameter actually varies and (in the star harness) that both fence branches are actually reached.
- **Verified by mutation, not observation:** dropping the parenthesization (`where_clause.rs:93`) reds `differential_proptest`; dropping the predicate from the grain CTE (`per_grain.rs:1044`) reds `star_schema_proptest`. A generator that varies but whose assertions cannot fail is the failure mode this entry exists to prevent, so "it passes" was not accepted as evidence.
- **Also closed (2026-08-04): `semi_additive_proptest`**, the highest-priority of the three and the path EXP-9 lived on. Here the predicate is applied *before* the `RANK` inside `__sv_snapshot`, so it does not merely shrink what is summed — it changes **which row wins the snapshot**: filtering away the `MAX(ts)` row promotes the next timestamp. The oracle therefore splices the predicate into *every* reference to the base table, including the subquery that determines the snapshot timestamp; filtering only the outer aggregate would encode post-snapshot filtering and would agree with an implementation making the same mistake.
  - Two verifications, because a passing randomized property is not by itself evidence here. Dropping the predicate from the snapshot CTE (`semi_additive.rs:297`) reds the property. And `predicate_is_applied_before_the_snapshot_not_after` pins the distinction deterministically: on one entity with rows at `ts=2`/`ts=1` under `where_clause := 'ts < 2'`, before-snapshot filtering yields balance 10 while after-snapshot filtering yields no rows — the test asserts the two formulations *disagree* as well as asserting the extension matches the former, so it fails if the comparison ever becomes insensitive to the distinction.
  - The generator-coverage guard additionally asserts that an ACTIVE snapshot combined with a predicate on the NA dimension is actually generated — the only shape that distinguishes before from after, and the one whose absence would make the whole extension inert.
- **Finally closed (2026-08-04): `window_metric_proptest` and `multi_hop_join_proptest`.**
  - **Window:** the predicate is injected into `__sv_agg`, *before* the window function runs, so it does two things at once — it changes each surviving group's inner `SUM`, and when it empties a group it removes that row from the partition the window aggregates over. The oracle filters the `agg` CTE and nothing else; the correlated subquery reads from the already-filtered CTE, so partition membership follows. Its coverage guard asserts predicates on a queried dimension *outside* the effective partition are generated — the shape where the window value moves while the partition key does not.
  - **Multi-hop:** the predicate is evaluated inside every grain's CTE, so the oracle filters each grain's half. It also gains a second fence property mirroring the existing dimension rule: a `where_clause` member **below** a selected metric's grain must be rejected, because joining it into that grain's CTE fans the metric (filtering on `t` while aggregating `sum(u.uw)` inflates the sum). Its guard asserts both branches are reached *and* that an accepted multi-grain query carries a predicate, which is the multi-grain injection the harness exists to cover.
  - Both mutation-verified: dropping the injection at `window.rs:236` reds the window property; dropping it at `per_grain.rs:1044` reds the multi-hop property. Both reverted.
- **Result:** all five numeric harnesses now generate and oracle-check a `where_clause`. The two remaining `where_clause: None` sites in `tests/` are in `expand_proptest.rs`, which checks structural parse/expand invariants rather than comparing numbers against an oracle — a predicate there would not be checked for correctness, so it is deliberately out of scope.
- **What this makes true:** CLAUDE.md's rule that a new query-semantics feature must reach the numeric oracles is only as good as the harnesses it points at. All five can now see a predicate, and each carries a generator-coverage guard so the parameter cannot silently revert to an inert default without a test failing.

### 44. ✅ Schema-scoping migration stored the row's schema spelling, not the catalog's (CAT-1) — RESOLVED 2026-08-04

- **Origin:** code review 2026-08-03 (`_notes/code-review-2026-08-03.md`, CAT-1).
- **Was:** `migrated_row` recorded whatever `schema_name` the legacy definition JSON carried, verbatim. `current_schema()` echoes the spelling last written in `USE`, so a view created after `USE "ANALYTICS"` recorded `ANALYTICS` for a schema the catalog itself calls `analytics` — a spelling the catalog never had. `create_target_schema_expr` already canonicalises at CREATE time (via `duckdb_schemas()`); the migration did not, so the two paths disagreed.

Both the `schema_name` column **and** the `schema_name` inside the stored JSON are rewritten, because the module documents them as being in lockstep and the SHOW / DESCRIBE listings read the JSON.

  - No collision risk: the legacy table is keyed on `name` alone, so there is at most one row per name and canonicalisation cannot merge two rows into one key.
- **Coverage:** `catalog::tests::schema_scoped_storage_tests::{migration_records_the_catalogs_schema_spelling_not_the_rows, migration_keeps_column_and_json_schema_in_lockstep_when_canonicalising, migration_keeps_an_unknown_schema_spelling_rather_than_dropping_the_row, migration_leaves_an_already_canonical_spelling_alone}`, plus `test/integration/test_legacy_catalog_schema_spelling.py` (`just test-legacy-schema-spelling`), which builds a real pre-scoping `.db`, migrates it through a real `LOAD`, and asserts the duplicate-row/stale-read symptom is gone. That integration test also closes part of TC-1's gap — the legacy-catalog migration is no longer unit-simulated only.

### 58. ✅ The YAML → GET_DDL round-trip contract is now enforced, and the fuzz oracle can no longer look away (RT-5/RT-6) — RESOLVED 2026-08-07

> **Correction 2026-08-08.** The contract statement below was **false when written**, for four classes of field the RT-5/RT-6 enumeration never reached — it covered identifier *slots* only. Free-expression slots admitted comment markers that destroyed sibling members on replay (RT-8); the entire `WindowSpec` payload was emitted raw, so a hostile `frame_clause` injected a metric and a partition dimension named `rows` silently became a frame clause (MODEL-1); the semantic cross-references (`NON ADDITIVE BY` dimensions, window inner metric and partition/order dimensions, materialization names and references) were validated on the DDL path only (MODEL-1); `output_type` was dropped entirely (RT-7, now #68); and a bare derived metric named `private`/`public` re-parsed as an access modifier (RT-9). All are closed as of the 2026-08-08 change, which extended the contract to free-expression slots, the window payload, cross-references (now shared with the parser via `body_parser/cross_refs.rs` rather than duplicated) and entry-initial keyword collisions.

- **Origin:** code-review 2026-08-06 RT-5 (HIGH) / RT-6 (MEDIUM). The review notes no TECH-DEBT entry existed for this contract at all — this is that entry.
- **Was:** YAML is the only surface that reaches a `SemanticViewDefinition` without passing through the clause parsers, and it performed NO identifier-syntax validation. `GET_DDL` then rendered those slots verbatim. Verified against the renderer: a join with no `name` rendered `     AS o(customer_id) REFERENCES c`; a dimension with no `source_table` rendered `region AS c.region` — both DDL this project's own parser rejects. Worse and silent: `source_table: "a.b"` with `name: "region"` rendered `a.b.region AS …`, which re-parses cleanly as source table `a`, name `b.region` — a **different model**, no error anywhere. And `pk_columns: ["a--b"]` rendered `PRIMARY KEY (a--b)`, which the front door's comment-blanking pre-pass truncates to end-of-line.
- **Why no fuzzing caught it:** the contract broke exactly where the oracle stopped looking. `fuzz_render_roundtrip` (mirrored in `render_ddl.rs`) **returned without asserting** when `parse(render(def))` failed — so `Arbitrary` generated `name: None`, render emitted unparseable DDL, and the target classified its own finding as unreachable input and stayed green. Its second escape, on a re-parse of freshly-rendered CANONICAL DDL, deferred to `tests/roundtrip_proptest.rs` — whose generators pinned `name: Some("rel{i}")` and `source_table: Some(...)`, so that harness structurally could not reach the shapes. Each half pointed at the other.
- **Resolution (2026-08-07):**
  - `model::validate_ddl_representable` states the reachability rule for a stored definition and is called from `from_yaml_with_size_cap`, the single choke point both YAML entry points (`rewrite_ddl_yaml_body`, the ALTER FFI path) pass through. Split per clause over four shared slot predicates.
  - Two things were probed against the grammar rather than assumed, and both changed the fix: dimensions and facts REQUIRE a source table but metrics do NOT (a derived metric is legitimately unqualified — a validator written from the finding's text would have rejected every YAML-imported derived metric); and `identifier_slot_error` alone is insufficient, since it accepts `a.b` (a qualified identifier is a valid identifier — it is the SLOT that admits one part) and accepts `a--b` / `a/*x*/b` outright, having no comment awareness. Single-identifier slots therefore also require exactly one qualifier part, and every slot must survive `blank_sql_comments` unchanged.
  - The fuzz oracle's second escape is **gone** and stays gone: `d1` comes from the parser, so `render(d1)` failing to re-parse is a contract break by definition. Its *first* escape was initially replaced by a `validate_ddl_representable` precondition; that attempt was reverted after eight rounds of fuzzing — see **#60** for why, and for what the target asserts now.
  - `tests/common/mod.rs` no longer pins the relationship name to `rel{i}`; it is generated from `arb_stored_ident()`, so quoted and unicode relationship names have round-trip coverage they never had.
- **What removing the escape immediately found (2026-08-07):** CI's `fuzz_render_roundtrip` went red on the first run against the tightened oracle, on a definition with a TABLES clause **and nothing else**. That is not an identifier-slot defect at all: `find_clause_bounds` requires TABLES *and* at least one of DIMENSIONS / METRICS, so `GET_DDL` on such a definition emits a lone TABLES clause — a body its own parser refuses. The validator was checking what every slot *contained* and never that the clause set was one the grammar could produce. It now runs `validate_yaml_structure` first, scoped to `!def.tables.is_empty()` so legacy no-tables definitions (which `render_create_ddl` declines to render at all) stay importable. The function is named `validate_ddl_representable` rather than `validate_identifier_slots` because the rule is no longer only about slots.
  - Hand-probing the same boundary turned up three more, two of them in the *opposite* direction — slots the validator refused that the DDL grammar accepts and `GET_DDL` round-trips byte-identically. A relationship name is validated in DDL by `identifier_slot_error`, which accepts `a.b`; a materialization's TABLE is a *physical* table, where `schema.table` is the ordinary spelling. Both were being sent through the single-identifier predicate, so YAML was rejecting definitions the DDL path accepts — a regression this PR would have introduced. They now use `slot_qualified`. (Raised in review on PR #209; confirmed against the parser and the renderer before being accepted, and each relaxation is pinned by a control asserting the multi-token form is still refused.)
  - **Round two, same oracle:** the next CI run shrank to a metric with an **empty expression**, rendering `e.p  AS ` — "Missing expression after 'AS'". Every member is `name AS expr` and the clause parsers require the expression, but the validator had only ever looked at names and slots, never at the payload. Bisecting that crash field-by-field cleared every other suspect in it — a NUL-bearing alias, a table name full of spaces, and a trailing-space member name all round-trip, because the renderer quotes them — so the fix (`member_expr`) is deliberately narrow, and covers dimensions and facts as well as metrics since all three share the shape. The rest of the member payload was probed in the same batch and left alone: comments containing quotes / newlines / nothing, synonyms containing quotes / parens / nothing, and `output_type` empty, spacey or malformed all round-trip.
  - **Round three — an oracle bug, not a product one.** A local 600s run (cargo-fuzz installed so the target could be reproduced the way CI runs it, instead of discovering each finding a push at a time) failed at the *stage-2* assertion on a definition whose `pk_columns` contained `""`. The precondition already rejected that input — and rejected the parser-produced `d1` derived from it — but RT-5 had wired the precondition in **lazily**, consulting it only inside the stage-1 parse-failure branch. When stage 1 happened to parse, the target went on to assert against a chain rooted in a definition no entry point can store, and reported the result as render/parse drift. The precondition now runs UP FRONT in both the fuzz target and its `render_ddl.rs` mirror, which is what its own doc comment always claimed it did. This is not a restored escape: it applies the same stated rule consistently, where before it applied it in one branch out of two.
  - Diagnosing that one turned up a genuine DDL-side parser defect, unrelated to YAML and out of scope here — recorded as **#59**.
  - All crash artifacts are committed under `fuzz/seeds/fuzz_render_roundtrip/`, byte-identical to CI's uploads.
  - The third: `identifier_slot_error` returns `None` for an all-whitespace slot by design — its DDL call sites report emptiness themselves, from clause context the validator does not have — so a relationship named `"  "` passed and rendered as `      AS o(cid) REFERENCES c`. The emptiness check now lives in `slot_common`, which is that call site. Separately, `TableRef.table` was unvalidated; it is emitted through `emit_table`, which quotes anything that would not re-parse verbatim (a space, a depth-0 comma, a `--` run — each probed and each round-trips), so the one value it cannot protect is the empty string, and that is deliberately the only thing checked there rather than a full slot predicate.
- **Residual:** the generator still pins table aliases to `t{i}` and join FK/ref columns to bare ASCII (deliberate — the harness's hostile-identifier surface lives in member names and payloads), and `arb_payload` contains no newline, so multi-line comments never round-trip. Recorded here rather than left implicit.
- **Residual (strictness, not correctness):** `validate_ddl_representable` is in a few places stricter than the DDL parser on values that *do* round-trip — a materialization TABLE of `a, b`, for instance, is accepted by the MATERIALIZATIONS sub-clause parser (which reads the slot as free text) and refused here by the shared identifier-slot rule. Those are nonsense table names that would fail at query time regardless, so the stricter rule is the intended one; it is recorded because it means YAML import and DDL do not accept exactly the same language, only the same *round-trippable* one.

### 59. ❌ The METRICS parser accepts an entry with NO NAME when `USING (…)` precedes the `AS` — OPEN

- **Origin:** found 2026-08-07 while diagnosing a `fuzz_render_roundtrip` failure on PR #209. Not part of the 2026-08-06 review; a pre-existing DDL-side bug that surfaced because RT-5 tightened the oracle.
- **What it is:** the metric-entry parser has a "Missing metric name before 'AS'" check, and it works — `METRICS ( AS x )` is rejected. But put a `USING (…)` clause in front and the same nameless entry is **accepted**:

  ```
  METRICS (
       USING () AS  COMMENT = ''
  )
  ```

  parses to `Metric { name: "", expr: "", … }`. Confirmed by running that exact body through `parse_keyword_body`; the two spellings differ only in the `USING ()`, and only one is refused. So the name check is not reached on the `USING`-bearing path.
- **Why it matters:** the stored definition is unrepresentable. `GET_DDL` renders it back as `     AS  COMMENT = ''`, which this project's own parser then refuses with "Missing metric name before 'AS'" — the same GET_DDL-emits-unreplayable-DDL class as RT-5/RT-6, but reached through DDL rather than YAML, so the YAML-side `validate_ddl_representable` cannot prevent it. An empty `expr` on the same path is the second half of it.
- **Why it is not fixed here:** PR #209's scope is the YAML → `GET_DDL` contract (RT-5/RT-6). This is a DDL-side parser defect in a different module, with its own test surface, and folding it in would mean a parser change riding along in a validation PR. Recorded rather than silently carried.
- **What would finish it:** move the empty-name check in `body_parser/metrics.rs` so it runs on every path into a metric entry rather than only the no-`USING` one, and pair it with the same check for an empty expression; then extend `validate_ddl_representable`'s member rules with a `.test` case going through real DDL, since the YAML side already covers the equivalent shapes.
- **Not currently caught by fuzzing:** no target reaches it. `fuzz_render_roundtrip` starts from a `SemanticViewDefinition` and only ever *renders* — the defect is on the way IN, in what the DDL parser accepts, so the empty-name definition it would need is one the target's stage 0 discards rather than constructs (see **#60**). Catching it needs a target that fuzzes DDL **text** through `parse_keyword_body` and asserts that whatever parses can be re-rendered and re-parsed; that is the same missing target #60 describes, and it would cover both. The reproducing body is quoted above so this does not depend on the fuzzer to be rediscovered.

### 83. ❌ A bare column in a member expression binds against every joined table, not the member's own (same-name ambiguity; cross-table bare references) — OPEN

- **Origin:** found 2026-10-13 while reproducing the Snowflake D1 fixture for #71: the fixture writes `o.order_id AS o_id`, and `o_id` is also a column of `li`. Pre-existing on `main`; not caused by #71.
- **Snowflake's rule:** a member expression is scoped to its own logical table — a bare column is that table's column, and "expressions cannot refer to base table columns from other tables". This extension splices the expression verbatim into whatever `FROM` the query needs, so a bare column is resolved by DuckDB against every table joined there. `graph::validate_member_references` (#52, PAR-3) enforces the scoping rule only for **qualified** references.
- **Symptom 1, same-name collision (loud).** A bare `o_id` in a member on `o` or `li` raises DuckDB's `Ambiguous reference to column name "o_id"` whenever a query joins both tables — for metrics, dimensions and facts, on the home-anchored, multi-grain, dimensions-only and FACTS paths alike. Never a wrong number. Documented as a limitation (`docs/reference/create-semantic-view.rst`, "Column qualification in expressions"), with qualifying as the workaround. #71 does not widen it: in a tree of many-to-one edges, the path from a metric's table to the dimension tables is a subset of the paths from the base table to both, so home anchoring never joins a table the base-anchored path would not. It narrows it where the home table alone suffices (`SUM(o_id)` on `li` with no dimension now binds to `li.o_id`; it was ambiguous).
- **Symptom 2, cross-table bare reference (silent).** `li.li_amount AS SUM(amount)`, where `amount` exists only on `o`, is accepted at CREATE and binds to `o.amount` whenever `o` is joined — summing each order's amount once per line item, a cross-grain number no line-item column produced. Whether `o` is joined depends on the query shape, so the same metric is a silent number in one query and a `"amount" not found` error in another. #71 moved one shape across that line: with no dimension, the metric used to return the silent number through the base-anchored join and now errors (scanning `li` alone).
- **What would finish it — the Snowflake rule, applied at expansion.** Qualify each bare column in a member expression with the member's own table alias before splicing (dimension, fact, metric, `NON ADDITIVE BY` and window references alike), and reject a bare name that is neither a column of the member's table nor a member name, with a message naming the rule (the same one PAR-3 gives for qualified references). Both halves need the physical column list of each table, which the definition does not store. It is available at query bind time (the table function already binds probe queries, `query::table_function::try_infer_schema`) and is **not** reliably available at CREATE (#19: the lowered DML binds on a fresh connection that cannot see same-transaction tables), which is why rejecting at CREATE alone cannot work. The rewrite must also not touch identifiers in non-column positions — a type name in `CAST(x AS date)` / `x::date`, an `INTERVAL` unit, an `EXTRACT` field, a lambda parameter, a named-argument key — and must settle the precedence of a name that is both a column of the table and a member name. That is a scanner-class change (the PARSE-12 history applies), so it is deliberately not folded into #71.
- **Coverage of the current state:** `src/expand/tests_bare_column_scoping.rs` (one test per path; the two `known_gap_*` tests pin the wrong answer and flip when this is fixed) and `test/sql/bare_column_scoping.test`.

### 82. ❌ Metric queries that stay base-anchored after #71, and the row-level paths that keep base-anchored semantics — OPEN

- **Origin:** opened 2026-10-13 by the #71 fix. Numbered 82 because 78–81 were already taken on `main` when it merged.
- **What is degraded.** #71 makes every metric aggregate from its own home table, but the per-grain planner still declines some shapes and leaves them on the base-anchored `FROM base LEFT JOIN …` path. There a child metric keeps the pre-#71 answer: orphan child rows (NULL FK) are dropped and a childless parent gets a row (`0` for COUNT, guarded by `facts::guard_aggregate_args` / `CountStarRequiresPrimaryKey`). Changing them changes *which rows* a non-aggregate query returns, which is a separate decision from #71's metric semantics, and `phantom_row_filter` (#67) already fences the childless-parent half.

Then re-anchor dimensions-only and FACTS queries at the members' own table, with a decision recorded on the row set.
- **Coverage of the degraded state:** `tests_phantom_row_guard.rs` and `tests_count_star_rewrite.rs` reach the fallback through an unqualified dimension and pin its (guarded) numbers and errors; `cr20260808_phantom_row_guard.test` pins the unchanged FACTS / dimensions-only rows.

### 79. ✅ Relationship names are not required to be unique — RESOLVED 2026-10-13

- **Origin:** found 2026-10-13 while migrating the relationship-name sites onto `ident_matches` (#28). Pre-existing on `main` at 9ec0134.
- **Symptom:** two relationships could share a name as long as they were not a role-playing pair to one table — e.g. `r AS f(departure_code) REFERENCES a, r AS f(carrier_code) REFERENCES c` was accepted. Every lookup by name (`USING (r)` validation, the join resolver, the role-playing fence, the fact rewrite, the per-grain path) takes the FIRST relationship with that name, so `USING (r)` silently meant whichever was declared first. Only the role-playing diamond check (`check_no_diamonds`) compared names, and only among relationships to the same target.
- **Snowflake:** relationship names are identifiers in one namespace per view and must be unique.
- **Resolution:** `check_relationship_names_unique` (`src/graph/relationship.rs`) runs in `validate_graph` right after the FK-column check, keyed on `ident::ident_key` (quotes stripped and case folded per identifier part, as `ident::normalize_ident_part` does, but with the parts kept apart), so `r`, `R` and `"r"` are one name while the two-part `x.y` and the one-part `"x.y"` are two (PR #249 review: keying on the joined `normalize_ident_part` string rejected that distinct pair as a duplicate). The error names both declarations: `duplicate relationship name 'route': 'route' (f -> a) and '"ROUTE"' (f -> c) name the same relationship; …`. It runs before the diamond check, so a role-playing pair that repeats a name now gets this message instead of `diamond: two paths to 'a' via 'f' and 'f'`. DDL and YAML both reach it (`enrich_definition_for_create`). CREATE-only: a stored row with a duplicate name keeps loading, with "first wins" reads. The name check inside `check_no_diamonds` keys on the role's scoped join alias (`<table>__<normalize_ident_part(name)>`), so it now rejects only two role-playing names that are distinct relationship names but would share one alias (`x.y` and `"x.y"` to one table), with `relationships 'x.y' and '"x.y"' to 'a' would both be joined as 'a__x.y'; …`.
- **Lookup by name (PR #249 review):** every site that finds a relationship by name — `USING` validation (`graph/using.rs`), the join resolver, the #69 fact fence and `find_using_context` (`expand/role_playing.rs`), the fact rewrite (`expand/facts.rs`) and the per-grain gate and join emission (`expand/per_grain.rs`) — goes through `graph::RelNameMatch` / `graph::find_relationship`. It matches by spelling (ASCII case-insensitive, the pre-#249 rule) when any declared name has the requested spelling, and by `ident_key` otherwise. A view CREATE accepted since this entry has names unique under `ident_key`, so the two rules agree; the spelling-first rule is for a row stored earlier that holds `dep` and `"dep"` as two roles of one table (then accepted by the diamond check), so `USING ("dep")` keeps meaning the quoted edge instead of whichever was declared first. Role deduplication in the fences is by resolved edge, so such a row keeps its two roles (ambiguous where it was ambiguous).
- **Coverage:** unit tests `duplicate_relationship_names_to_different_targets_rejected`, `…_differing_in_case_and_quoting_rejected`, `duplicate_role_playing_relationship_names_get_the_duplicate_name_error` (each confirmed red individually before the fix) and the control `distinct_relationship_names_accepted`; `role_playing_names_differing_only_in_quoting_are_one_name` now expects the duplicate-name message. `relationship_names_and_qualifiers.test`: DDL different-target, case/quoting and role-playing cases and a YAML case (each confirmed red in its own file against the unfixed build), a distinct-names control that queries, and a stored-row guard that injects a duplicate-name definition and queries it. `role_playing_facts_and_quoted_names.test`'s `dep` / `"dep"` case now expects the new message. ### 77. ❌ `SHOW SEMANTIC …` / `DESCRIBE SEMANTIC VIEW` cannot be used as a subquery — revisit with the DuckDB 2.0 PEG parser — OPEN

- **Origin:** the v0.13.0 docs audit (PR #242, 2026-10-01). Six doc examples had shipped since v0.5.4–v0.7.0 filtering introspection output in the DuckDB idiom, `SELECT … FROM (DESCRIBE SEMANTIC VIEW v) WHERE object_kind = 'DIMENSION'` and `SELECT … FROM (SHOW SEMANTIC VIEWS)`. All six are parser errors (`syntax error at or near "VIEW"`). No test or example script ran them, so they went unnoticed until the audit executed them.
- **Why it is natural to expect:** DuckDB accepts its own introspection statements in subquery position. On 1.5.6, `SELECT column_name FROM (DESCRIBE t) WHERE …` and `SELECT count(*) FROM (SHOW TABLES)` both work. Users who know DuckDB will reach for the same form with ours.
- **Why it fails:** DuckDB's grammar doesn't know our statements. We recognise them ourselves, but only at the start of a statement: the `parser_override` entry point (`src/parse/ffi.rs`) asks `detect_ddl_kind` in `src/parse/detect.rs` whether the statement starts with one of our statements (v0.5.x used the same prefix test in `detect_ddl_prefix`). `SELECT * FROM (DESCRIBE SEMANTIC VIEW v)` starts with `SELECT`, so the extension never sees it and DuckDB's parser rejects the inner text. Supporting it today would mean finding and rewriting our statements inside arbitrary SQL with the string scanners. That's a large, fragile surface, not worth building against the current parser-extension API.
- **What we ship instead (the interim state):**
  - The docs say plainly that these statements can't be subqueries (`docs/reference/functions.rst` `ref-functions-subqueries`, with notes on the DESCRIBE and SHOW SEMANTIC VIEWS pages), and the six examples were removed.
  - We deliberately do **not** recommend calling the backing table functions as a FROM workaround. They're implementation details of the statements, and their `duckdb_functions()` descriptions say "use the statement rather than calling this directly".
  - The one documented exception is the `GET_DDL` dump-every-view recipe in `docs/reference/get-ddl.rst`, which reads `FROM list_semantic_views()`. It predates this entry: `list_semantic_views`'s registered description carves it out, and `test/sql/function_descriptions.test` runs it.
  - `FROM describe_semantic_view('v')` does work, but it's undocumented on purpose.
- **Revisit when:** we move to a custom PEG grammar on **DuckDB 2.0**. With our statements as real grammar productions, they can appear wherever DuckDB allows its own `DESCRIBE` / `SHOW`, so no rewriting scanner is needed.
- **What would finish it:**
  - Make every statement the extension provides parse in subquery and CTE position:
    - `DESCRIBE SEMANTIC VIEW`
    - `SHOW [TERSE] SEMANTIC VIEWS`
    - `SHOW SEMANTIC {DIMENSIONS,METRICS,FACTS,MATERIALIZATIONS}` (with and without `IN <view>`)
    - `SHOW SEMANTIC DIMENSIONS … FOR METRIC`
    - `SHOW COLUMNS IN SEMANTIC VIEW`
  - Add sqllogictest cases that filter, join and aggregate each one as a subquery.
  - Then restore the removed examples in statement form: filtering DESCRIBE output by `object_kind` (dimensions only, relationships only, count by kind, materialization rows only), and selecting or filtering `SHOW SEMANTIC VIEWS` columns.
  - Move the `GET_DDL` dump-every-view recipe to `FROM (SHOW SEMANTIC VIEWS)`, and drop the FROM-source carve-out from `list_semantic_views`'s description in `cpp/src/shim.cpp` and its check in `test/sql/function_descriptions.test`.
- **Docs to flip when it lands:**
  - `docs/reference/functions.rst` (`ref-functions-subqueries`)
  - `docs/reference/describe-semantic-view.rst` (`ref-describe-subquery` note)
  - `docs/reference/show-semantic-views.rst` (`ref-show-subquery` note)
  - `docs/reference/get-ddl.rst` (the dump-every-view recipe)
  - `docs/how-to/materializations.rst` (the "materialization rows come last" sentence)

### 76. ❌ Query-time scalar expressions in `dimensions` / `metrics` / `facts` are not supported — OPEN

- **Origin:** parity question 2026-09-30 — Snowflake accepts `SELECT * FROM SEMANTIC_VIEW(tpch_analysis DIMENSIONS DATE_PART('year', orders.order_date) AS year) ORDER BY year`; we have no equivalent.
- **Snowflake semantics** (`SEMANTIC_VIEW` construct reference): `DIMENSIONS` accepts "scalar expressions that refer to dimensions or facts in the semantic view", and "the dimensions and facts in that expression must belong to the same logical table"; `FACTS` has the same rule. `METRICS` accepts "an expression that includes scalar expressions that refer to metrics … [and aggregations of dimensions or facts]". Every item takes an optional `AS <alias>`, which names the output column.
- **What we do today:** every `dimensions := [...]` / `metrics := [...]` / `facts := [...]` item is a member **name**, resolved by `expand::resolution::find_dimension` / `find_metric` (and the `Resolvable` impls in `expand/sql_gen.rs`). An expression is not parsed. It fails with `unknown dimension '<the whole item text>'` (the dotted-name split in `find_dimension` just finds no member to match). There is no query-side `AS` alias either: the output column is always the member's name. The only query-time expression surface is `where_clause`, which filters and never groups.
- **Workaround:** declare the derived member in the DDL (`orders.order_year AS DATE_PART('year', orders.o_orderdate)`). Querying the finer dimension and re-grouping outside `semantic_view()` gives the right number only for additive metrics. COUNT DISTINCT, ratios, semi-additive and window metrics come out wrong, which is why this needs to happen inside the expansion rather than be left to the caller.
- **What would finish it** — the member-reference half already exists in `expand/where_clause.rs` (a quote-aware `expr_tokens` scan substituting declared dimensions/facts to their expressions, with PRIVATE and qualified-reference handling from #47). An expression item needs:
  - an item grammar `<expr> [AS <alias>]`, split at a top-level `AS` using the same quote-aware scanner. Alias-less expressions need a deterministic output name, and aliases must not collide with each other or with named members (`DuplicateDimension`).
  - enforcement of Snowflake's same-logical-table rule for dimension/fact expressions, with a clean error when it is broken.
  - the expression's GROUP BY key being the **substituted** expression, not the alias, on every emission path: base-anchored, per-grain CTEs (grain assignment follows the referenced members' table), semi-additive `__sv_snapshot` partitioning, window `__sv_agg`, and materialization routing, which must decline or match on the expression rather than on a member name.
  - for `metrics`, an outer expression over metrics composes like a query-local derived metric and inherits #55's limit on composing over a snapshot. Aggregations of dimensions or facts are a separate, larger feature (an ad-hoc metric) and could ship later.
- **Fences this walks past** (per CLAUDE.md): the members an expression references make their tables reachable, so each one must go through the same fan-trap check as a named queried dimension (`expand::fan_trap::check_fan_traps`), role-playing ambiguity/`USING` resolution, and source-table reachability as a named queried dimension. The `where_clause` history (EXP-27/EXP-31) is what goes wrong when one fence is missed.
- **Coverage it would need:** it changes what number a query returns, so at least one differential proptest (`star_schema_proptest` or `multi_hop_join_proptest`) must generate expression dimensions and mirror them into its oracle, beyond fixed `.test` rows.
- **Docs:** listed as not supported in the parity table in `docs/explanation/snowflake-comparison.rst` ("Feature Parity Notes"). Flip that row when this lands.

### 72. ✅ A disconnected base table is accepted at CREATE and emits unbindable SQL — RESOLVED 2026-10-12

- **Origin:** found 2026-08-08 while closing TC-12(d) — the substring-only assertions in `src/expand/tests_fact_query.rs` were hiding it. Every definition in that file declared a fourth table joined to nothing; because it was declared first it became the graph root, and the tests asserted on SQL text rather than running it, so nobody noticed the SQL could not bind. (That fixture was already repaired in TC-12; no other fixture relied on a disconnected graph — the full `cargo test` and sqllogictest suites pass with the check in place.)
- **Symptom:** if the first table in `TABLES` had no relationship edge, `validate_graph` accepted the definition — `check_no_orphans` exempts the root node, and "root" is just *first in the TABLES clause* — but every query emitted `FROM "<root>" AS "<root>" LEFT JOIN … ON … = "<other>"."<col>"`, a reference to an alias never in scope: `Binder Error: Referenced table "o" not found`. ### 71. ✅ A metric's VALUE changed depending on which other metrics were queried with it (MM-3) — RESOLVED 2026-10-13

- **Origin:** found 2026-08-08 by `tests/metamorphic_proptest.rs`, the first harness to check "a metric queried alone equals the same metric queried alongside others" (`_notes/proactive-defect-discovery.md` §2.1(a)). Not reachable by any oracled harness, because each of those fixed a request shape and compared against a hand-written expectation for *that* shape.
- **Symptom, on legal data:** a single-grain request was base-anchored (`FROM o LEFT JOIN li`); adding a metric of another grain routed the request through `per_grain`, which anchors each grain's CTE at its own table (`FROM li`). The two disagreed in two independent ways: a child row whose **foreign key is NULL** was dropped by the base-anchored join and counted by the child-anchored CTE (`SUM(li.amount)` = 12 alone, 112 co-queried), and a base row with **no children** contributed `COUNT = 0` to the base-anchored query but *no row* to the child-anchored CTE, so the FULL OUTER JOIN reported `NULL` (`n_li` = 0 alone, NULL co-queried). A query's metric set silently selected the semantics.
- **Decision (D1, settled against Snowflake 2026-10-13 with Anentropic's fixture `d1-snowflake-fixture.sql`):** every metric is aggregated from its **own home table**, joining outward many-to-one to reach the queried dimensions; per-grain blocks are FULL OUTER merged. Consequently an orphan child row (NULL FK) is counted under a NULL dimension value; a childless parent's child COUNT is NULL, not 0, when a parent-grain metric brings its row in; a child metric queried alone gives **no row** for a childless parent; and co-querying never changes a value. The multi-grain row set is the union of the grains' row sets.
- **Resolution:** `per_grain::plan` routes a query through the per-grain emitter whenever any metric grain is not the root (it used to fire only where a base-anchored FROM would *inflate* a metric). The single-CTE re-anchors (`snapshot_cte_anchor`, `window_cte_anchor`) re-anchor in either direction, not only toward a parent. A metric `USING` relationship whose target table no queried dimension or `where_clause` member reaches no longer keeps the query base-anchored (it scoped nothing there either), and a `USING` metric over a fact on the role-played table gets its scoped join emitted inside its own grain CTE. Every anchored emitter (grain CTEs, the window `__sv_agg`, the semi-additive snapshot) takes its joins from `per_grain::anchor_needs`: the inlined-fact tables bare, and the `USING`-selected instances scoped (`AnchorNeeds::scoped`, joined by `anchor_joins`), decided per metric exactly as `facts::rewrite_using_scoped_refs` requalifies that metric's text. The `CountStarRequiresPrimaryKey` check now fires only on the base-anchored path, since a home-table scan has no NULL-extended rows. Only an all-root query, and the fallbacks listed in **#82**, remain base-anchored — on an all-root query the base table *is* every metric's home, so the two agree.
- **Changed results, deliberately:** a child-table metric queried on its own (or alongside only other child-grain metrics) now counts orphan child rows and returns no row for a childless parent, where it used to drop orphans and return `0` / `NULL` rows for childless parents. `COUNT(*)` / constant-argument aggregates on a PK-less child table are now answered rather than refused. Each changed `.test` expectation carries a "before #71" note.
- **Not changed:** dimensions-only and FACTS queries keep their base-anchored row semantics (recorded as a divergence in **#82**).
- **Coverage:** `mm3_metric_value_changes_when_co_queried_across_grains` and `mm4_childless_parent_manufactures_a_null_group_under_a_child_dimension` are live (both confirmed red with the fix reverted). Properties (a) and (b) of `tests/metamorphic_proptest.rs` are no longer scoped to single-grain metric sets: the generator draws mixed-grain chains and roll-ups, with anti-vacuity floors on each. `tests/child_grain_proptest.rs`'s oracle is rewritten to the home-table semantics (scan the child, look up the parent), its generator produces orphans and childless parents and groups by a child dimension, with anti-vacuity counts on each. `src/expand/tests_home_anchoring.rs` reproduces the Snowflake fixture's Q1–Q6 grids plus one case per emission path (derived, `where_clause` on parent and child members, semi-additive, window, PK-less `COUNT(*)`, role-playing), and `test/sql/d1_home_table_anchoring.test` / `d1_home_table_anchoring_paths.test` pin the same end to end (each query confirmed red on its own against the pre-fix build, except Q2 / Q4 / Q6, which were already computed per grain and pass on both).

### 68. ❌ `output_type` is refused at YAML import because no DDL clause can carry it (RT-7) — OPEN

- **Origin:** code review 2026-08-08 (`_notes/code-review-2026-08-08.md`, RT-7). Filed MEDIUM.
- **Was:** `output_type` (dimension / fact / metric) was settable only from YAML, and `render_ddl` has no emit site for it. `GET_DDL` — the documented dump/restore path — dropped it silently: the replayed view lost the `CAST(expr AS <type>)` at every projection site (`expand/sql_gen.rs:277,287,706,720`, `per_grain.rs:1002,1139,1150,1250`, `window.rs:185,338`, `semi_additive.rs:370,482`, `materialization.rs:124,133`) and the `data_type` every SHOW/DESCRIBE surface reports from it, with no error anywhere. So a definition was "YAML-storable" and not DDL-representable, contradicting #58's contract statement.
- **Resolution taken, and why it is a rejection rather than a fix:** `model::reject_output_type` refuses the field at the YAML choke point and names the equivalent `CAST(<expr> AS T)` in the message. The alternative — rendering the cast into the emitted expression — was **measured** and rejected: `expand::facts::inline_facts` / `inline_derived_metrics` splice a member's RAW `expr` into every referrer and never apply the cast, so moving the cast into `expr` would silently change what referring members compute (pinned by `tests/yaml_proptest.rs::output_type_is_not_applied_when_a_member_is_inlined`, which shows `SUM((o.qty))` versus `SUM((CAST(o.qty AS DOUBLE)))`), and the replayed definition would *still* carry `output_type: None`, leaving the contract false.
- **Why rejecting a documented, released field was judged acceptable:** the field's only semantic effect is reproducible by writing the cast into the expression, which round-trips correctly — so no capability is lost, only a spelling whose restore path was broken. What *was* lost is the sole route to a populated `data_type` column; **#51**'s read-side probe has since replaced it (resolved 2026-10-13).
- **What would finish it:** DDL grammar + renderer support for a declared member type. There is no Snowflake precedent — Snowflake's semantic-view DDL declares no member types — so this would be a deliberate divergence decision, not a parity gap. Read-side probing (#51, landed) already reports a member's actual type with no new syntax; a declared type would only matter for forcing a different one.
- **Known consequences, both loud where the old behaviour was silent:** (a) a `CREATE … FROM YAML` carrying `output_type` now fails with a message naming the field, the member and the `CAST` spelling; (b) `READ_YAML` on a *legacy* stored view that carries `output_type` exports YAML that can no longer be re-imported. Docs corrected in the same change (`docs/reference/yaml-format.rst`, `show-semantic-dimensions.rst`, `show-semantic-facts.rst`, `docs/explanation/snowflake-comparison.rst`).

### 67. ❌ Residuals of the generalized phantom-row guard (EXP-25/26/28/29) — OPEN, narrowed by #71

- **Origin:** code review 2026-08-08 (`_notes/code-review-2026-08-08.md`, EXP-25/26/28/29), opened by the fix for those findings. Supersedes the residual half of #56.
- **Narrowed 2026-10-13 by #71.** A metric query now aggregates each metric from its own home table, so on that path no phantom row exists and residuals **(1)**, **(2)** and **(4)** below no longer arise: `LIST(1)` on a childless parent gives no row (or NULL beside a parent-grain metric), a PK-less child needs no key, and a child dimension gains no phantom group. They are still live on the metric paths that stay base-anchored (**#82**), where the guard still runs and is still load-bearing; `src/expand/tests_phantom_row_guard.rs` pins them there through an unqualified dimension, and asserts the home-anchored answer for the same metric alongside. Residual **(3)** (row-level queries) and the cosmetic note are unchanged by #71.
- **What the fix does:** every synthesized join is a LEFT JOIN anchored at the base table, so a base row with no matching child survives as one NULL-extended "phantom" row. Aggregates now fence it by wrapping every aggregate argument in `CASE WHEN <pk> IS NOT NULL THEN … END` (`facts::guard_aggregate_args`), and row-level queries — a FACTS request and a dimensions-only `SELECT DISTINCT` — filter it with `WHERE <pk> IS NOT NULL` when every queried member lives on one table strictly below the base (`sql_gen::phantom_row_filter`).
- **What is therefore missing, (1) NULL-retaining aggregates.** The guard works by making the phantom's argument NULL, and every standard aggregate skips a NULL argument — except `list` / `array_agg`, which keep it as an element, and `first` / `last` / `arbitrary`, which can return it. `LIST(1)` on a childless parent now yields `[NULL]` where it yielded `[1]`: better, not right. Finishing it means emitting `AGG(x) FILTER (WHERE <pk> IS NOT NULL)` for that family (verified: `list(x) FILTER (WHERE FALSE)` is NULL, not `[NULL]`), which requires merging with a user-written `FILTER` clause and checking the `FILTER … OVER` composition on the window path.
- **What is therefore missing, (2) no PRIMARY KEY.** With no PK on the joined table there is no column that distinguishes a phantom, so the guard cannot run. Today that is a loud `CountStarRequiresPrimaryKey` for `COUNT(*)` and for an aggregate over a recognized constant LITERAL, and silence for everything else — `COUNT(1+0)` and `SUM(COALESCE(li.qty, 99))` on a PK-less child are still wrong. Deliberately not widened to "any aggregate on a PK-less joined table", which would newly reject `SUM(li.amount)` views that are correct today. Finishing it means guarding with the relationship's own key columns instead: a matched row necessarily has non-NULL join columns, so `<alias>.<fk-or-ref column> IS NOT NULL` is an exact substitute that needs no PK declaration.
- **What is therefore missing, (4) the AGGREGATE path still manufactures a NULL group under a child dimension (MM-4, found 2026-08-08 by `tests/metamorphic_proptest.rs`).** EXP-29 fenced the row-level shapes with `WHERE <pk> IS NOT NULL`; the aggregate path with the same member set guards each aggregate's *argument* instead, which fixes the value but not the **group key**. Grouping by a child dimension therefore still gains a phantom group: `SELECT li.qty, COUNT(li.id) … GROUP BY 1` gains `(NULL, 0)` when a childless parent is inserted, and `(NULL, NULL)` for `SUM`/`MAX`. Finishing it means applying the same `phantom_row_filter` predicate when every queried *dimension* resolves to one table strictly below the base, which is the aggregate twin of the EXP-29 fix. Resolved for the home-anchored path by #71: `mm4_childless_parent_manufactures_a_null_group_under_a_child_dimension` is live and green.
- **What is therefore missing, (3) row-level queries whose members span several tables.** `phantom_row_filter` applies only when the queried facts (or, for the dims-only branch, the queried dimensions) all live on ONE table below the base. Facts on two different child tables have no unambiguous grain — the emitted SQL is their cross product through the base — so that cell keeps the old behaviour rather than erroring, because the shape is reachable and its non-phantom rows are meaningful. A dims-only DISTINCT mixing a base and a child dimension is left alone deliberately and is not part of this gap: the base row is a legitimate member of that result even with no child.
- **Cosmetic, deliberately accepted:** the guard is applied once, at the shared base-metric resolution step, so it is also emitted on the per-grain / snapshot / window paths that anchor at the metric's own table and have no phantom to fence. It is a no-op there (the PK is non-NULL in a plain scan) but it makes the SQL noisier and adds a dependency on PK non-nullness where the query had none. Suppressing it needs the emission strategy to be known at resolution time, which today it is not.
- **Coverage:** `src/expand/tests_phantom_row_guard.rs` pins the resolved halves numerically, including both directions (a member ABOVE the base must NOT be filtered) and the no-PK error; `tests/child_grain_proptest.rs` randomizes them.

### 73. ✅ A typed literal separated from its introducer by whitespace still scans as a reference (PARSE-12 residual) — RESOLVED 2026-10-16

- **Origin:** PARSE-12's fix (code review 2026-08-08), narrowed during review of that change. Recorded per the rule that a knowingly-partial behaviour gets an entry in the same change.
- **What the fix does:** `expr_tokens::scan_chains` no longer emits an identifier chain as a *reference* when the chain is immediately followed by `'` — the adjacency rule `util::opens_escape_string` already uses. That covers `e'…'`, `E'…'` and the adjacent typed-literal form `DATE'2020-01-01'`, so a member named `e` or `date` can no longer corrupt those expressions.

A view declaring a member named `date` or `interval` therefore still risks the inline corruption PARSE-12 closed for the adjacent spelling.
- **Why it shipped narrow:** suppressing *every* identifier followed by whitespace and a string literal over-reaches badly — `SELECT foo 'bar'` is an alias, and ordinary expressions put identifiers before quoted text routinely. Doing it correctly needs a type-name registry so only real type introducers are suppressed, which is a larger change than the defect being fixed and carries its own false-positive risk.
- **What would finish it:** a small set of recognized type-name introducers (the SQL standard's plus DuckDB's aliases) consulted when a chain is followed by optional ASCII whitespace and `'`. Guard with a pinned unit test for the spaced form, alongside PARSE-12's adjacent-form tests.
- **Resolution (2026-10-16, COR-3, #93):** fixed by the broad rule after all, not a type registry. `scan_chains` treats any chain followed by optional whitespace and `'` as a type or keyword, including every word of a multi-word type (`TIMESTAMP WITH TIME ZONE '…'`). The alias concern above does not apply: the reference scan runs over single expressions (member definitions, `where_clause`), where a name followed by a string literal is not valid SQL, and the one whole-statement caller, `inject_search_path`, collects only function heads, which a chain followed by a string never is. Pinned by `a_spaced_typed_literal_prefix_is_not_a_reference` and `a_multi_word_typed_literal_type_is_not_a_reference`.

### 57. ❌ An unqualified `where_clause` member excludes a query from every re-anchoring path (EXP-22) — OPEN

- **Origin:** code review 2026-08-06 (`_notes/code-review-2026-08-06.md`, EXP-22), opened by the fix for that finding.
- **What the fix does:** the three re-anchoring deciders (`per_grain::is_eligible`, `snapshot_cte_anchor`, `window_cte_anchor`) now decline any query whose `where_clause` names a member with no `source_table`, exactly as they already decline a queried *dimension* with no `source_table`. Such a member is an unqualified expression: it is spliced into every CTE, so a re-anchored `FROM` rebinds it — silently, whenever the anchor table carries a column of that name, and to two *different* tables at once in a multi-grain plan.
- **What is therefore missing:** a query that combines an unqualified predicate member with a multi-grain or re-anchored shape now keeps the base-anchored path's outcome, which for genuinely multi-grain shapes is a fan-trap error rather than an answer. That is the correct conservative call — the dimension rule has worked this way since per-grain landed — but it is a capability gap, not a neutral choice. Finishing it means resolving an unqualified member against the base table explicitly (qualifying its expression at resolution time) so its binding stops moving with the anchor; then both the dimension rule and this one could be lifted together.
- **Residual in the same class, deliberately not fenced:** a predicate may also name something that resolves to **no** declared member — a raw column, which `resolve_where_clause` passes through verbatim by design so DuckDB validates it. A raw column binds against whatever the emitted `FROM` exposes and so has the same anchor-sensitivity. It is not fenced because the reference scan cannot distinguish a raw column from ordinary SQL that must survive (`NULL`, `TRUE`, `CURRENT_DATE`, `DATE '1995-01-01'`), so declining on any unresolved chain would decline nearly every predicate. Users who need a raw column in a predicate on a re-anchored query should qualify it.
- **Coverage:** three `tests_per_grain` tests, one per decider, each confirmed red individually, plus two controls pinning that a *qualified* member still re-anchors. `cr20260806_tier1_wrong_numbers.test` pins the end-to-end behaviour, including that the previously-silent case is now a loud ambiguity error.

### 56. ✅ The constant-argument aggregate guard was a whitelist and leaked four ways (EXP-21 residual) — RESOLVED 2026-08-08

- **Origin:** code review 2026-08-06 (`_notes/code-review-2026-08-06.md`, EXP-21), opened by the fix for that finding; closed by code review 2026-08-08 (EXP-25/EXP-26).
- **What the narrow fix did:** `facts::guard_constant_arg_aggregates` rewrote `<AGG>(<constant literal>)` to `<AGG>(CASE WHEN <pk> IS NOT NULL THEN <constant> END)` for five aggregate names (`COUNT`, `SUM`, `PRODUCT`, `LIST`, `ARRAY_AGG`) on a non-base source table.
- **Why the entry's own rationale was wrong.** It recorded two claims that do not hold. (1) `COUNT(DISTINCT <constant>)` "is genuinely multiplicity-invariant, so it needs nothing" — it is multiplicity-invariant and *existence*-sensitive, and the phantom row is not a duplicate but a row that should not exist: `COUNT(DISTINCT 1)` returned 1 for a childless parent where 0 is correct. (2) `MIN`/`MAX`/`AVG` were "outside the list because over a constant they are multiplicity-invariant" — true and irrelevant for the same reason: `MIN(1)` returned 1 where the empty-group answer is NULL. Two further escapes had no rationale at all: a constant *expression* is not a constant *literal* (`COUNT(1+0)` → 1), and any NULL-insensitive expression over the child's own columns resurrects the phantom (`SUM(COALESCE(li.qty, 99))` → 99), including a fact reference reaching another table (`SUM(<parent fact>)` → 25 vs 20). All numerically confirmed.
- **Resolution:** `facts::guard_aggregate_args` drops the per-argument classification entirely. On a non-base source table with a declared PRIMARY KEY, the FIRST argument of EVERY DuckDB aggregate is wrapped as `AGG([DISTINCT ]CASE WHEN <pk> IS NOT NULL THEN <arg> END)`. The wrap is neutral on real rows *whatever the argument is* — the PK is non-NULL there — which is exactly why it no longer needs to recognize the argument, and why the "the aggregate list is the load-bearing part" reasoning above no longer applies to arguments (it still applies to function NAMES, which are now matched as whole identifier words against DuckDB's aggregate catalog rather than as prefixes, so `sum_no_overflow(` is reachable at all). Later arguments, an in-call `ORDER BY`, and an outer `FILTER (WHERE …)` are copied verbatim; `COUNT(*)` is skipped so SG-8's star rewrite still owns it. Multi-argument aggregates — the gap this entry was originally opened for — are covered: every DuckDB aggregate drops a row whose first argument is NULL, so `STRING_AGG(CASE … END, ',')` is sufficient and the separator stays a constant of the call.
- **Coverage:** 28 tests in `src/expand/tests_phantom_row_guard.rs` (12 numeric reds confirmed individually), `test/sql/cr20260808_phantom_row_guard.test` end to end, and `tests/child_grain_proptest.rs` now generates all four escaped shapes against its correlated-subquery oracle (verified red with the fix reverted).
- **Residuals:** see #67.

### 55. ❌ A snapshot cannot be composed with an outer expression: a metric depending on a semi-additive metric errors (EXP-19/EXP-20) — OPEN

- **Origin:** code review 2026-08-06 (`_notes/code-review-2026-08-06.md`, EXP-19/EXP-20), opened by the fix for those findings.
- **What went wrong first:** `is_active_semi_additive`, the routing predicate that decides whether a query takes the `RANK`-CTE snapshot path, inspects only a metric's OWN `non_additive_by`. A metric that merely *depends* on a semi-additive metric — a derived metric referencing it, or a window metric naming it as its inner aggregate — therefore classified as regular, and the dependency's raw aggregate was inlined and evaluated over every row. `NON ADDITIVE BY` was silently discarded: with `balance` snapshotted at the latest `report_date` and `double_balance AS balance * 2`, querying the two returned 150/70 and 500/240 — not a 1:2 ratio, so wrong on its own terms, before any question of Snowflake parity. ### 54. ✅ A dimension expression is never fact-inlined, so a fact reference inside one is emitted verbatim — RESOLVED 2026-08-05

- **Origin:** found 2026-08-05 while addressing Copilot's review of #200, which asked whether the per-grain path collected fact tables referenced from *dimension* expressions. It does not — and neither should it, because the reference is never substituted in the first place.
- **Symptom:** `inline_facts` is applied to metric expressions and to other facts' expressions (`facts.rs`, the two call sites in `resolve_metric_exprs`), never to a dimension's. A dimension declared `tier_label AS c.cust_tier`, where `cust_tier` is a fact on `c`, emits `c.cust_tier AS "tier_label"` verbatim — a reference to a column that does not exist — so DuckDB fails on the unknown column whether or not `c` is joined. The DDL is accepted.
- **Why the join collection is metric-only:** PAR-6 (#53) briefly collected the tables reached from dimension expressions too. That joins a relation in order to satisfy a reference that is never inlined: it converts "unknown table `c`" into "unknown column `c.cust_tier`" and nothing more, while making the fan-trap fence report a fan trap for a construct that cannot bind either way. The collection was narrowed to metrics before #200 merged.
- **Resolved by inlining, not by rejecting, and the evidence settled it.** The entry left both options open. Probing first showed that a **same-table** fact reference in a dimension was broken too — `band AS CASE WHEN o.net_line > 100 …` over a fact on the dimension's own table emitted `o.net_line` verbatim. Snowflake's validation rules permit exactly that ("expressions can refer to base table columns **or other expressions** on the same logical table"), so this was a parity defect in the plain case rather than an unsupported cross-table extension, and rejecting it would have written the bug into the spec.
- **Resolution:** `facts::inline_dimension_facts` applies the same pass metrics already got, and every emitter that renders a dimension expression routes through it — the base-anchored SELECT, the grain CTEs, the facts path, the semi-additive snapshot and its `ORDER BY`, the window CTE, and `where_clause` members. Inlining runs *before* role-playing alias rewriting at each site, so a fact's own qualifier is rewritten with the rest of the expression.
- **The cross-table half came with it.** With dimension expressions inlined, the join collection and fan-trap fence that #200 narrowed to metrics are meaningful again and were restored, including the per-grain `anchor_joins` site Copilot flagged while reviewing #200 — correct about where the code was heading, though unreachable until the inlining existed.
- **Coverage:** `star_schema_proptest` grows a `uwd` dimension whose expression is the fact `u.uw1`, mirrored into the oracle as `u.w + 1`; because it is a *grouping key*, a mis-splice changes which rows collapse together, and the harness's parent-grain oracle was generalised from one parent-side dimension to N. Five `td54_*` unit tests cover the same-table, facts-path, `where_clause`, cross-table and grain-CTE shapes, each confirmed red individually. `member_reference_scoping.test` pins the numbers end to end.

### 53. ✅ A metric referencing a named fact on another table inlines the fact but never joins its table (PAR-6) — RESOLVED 2026-08-05

- **Origin:** found 2026-08-05 while verifying PAR-3 against Snowflake's validation rules. Not in the 2026-08-03 review; the review recorded cross-table *named-fact* references as working ("Named facts referenced across tables are inlined, `src/expand/facts.rs:168-195`"), which is true of the inlining and false of the join.
- **Symptom:** `o.mixed_margin AS SUM(o.amount - c.cust_discount)` where `cust_discount` is a fact on `c` expands to `SELECT ... SUM(o.amount - (c.discount)) FROM "orders" AS "o"` — the fact expression is spliced in, `customers` is not joined, and DuckDB raises an unknown-alias binder error at query time. The DDL is accepted: `validate_facts` / `validate_derived_metrics` / `validate_graph` all pass, verified by running the CREATE funnel's validator set over a body-parsed definition.
- **Why the two halves disagree:** `fact_replacement_map` deliberately keys each fact by its own `source_table.name` so that "a fact referenced across tables in its own-qualified form is then actually inlined, not just detected". `join_resolver` never got the matching change: it collects aliases from each member's declared `source_table` and, on the facts path, from *queried* facts (`fact_source_tables`) — never from facts a metric merely references.
- **Why it matters:** this is Snowflake's supported way to cross tables ("define facts on source tables, and finally refer to these expressions from connected logical tables"), and it is the workaround #52 would otherwise point users at. The failure is loud — the alias is unbound, so no query returns a wrong number — but the shape is fully DDL-reachable.
- **Resolution:** `facts::collect_referenced_facts` walks a member's expression for the facts it reaches — transitively, since facts chain and a derived metric reaches them through the base metrics inlined into it — and `join_resolver` adds each reached `source_table` to `needed`, alongside the aliases it already collected from declared `source_table`s and from queried facts.
- **The per-grain path needed the same change, and the numeric oracle is what found it.** A grain CTE inlines the referenced fact into the aggregate it computes, so it must join the fact's table for itself; the base-anchored fix alone left `__sv_grain_0` emitting an unbindable alias. `anchor_joins` now takes those tables through the extra-sources channel it already uses for `where_clause` member tables. This surfaced only after `star_schema_proptest` was taught to generate the construct — no hand-written example in the change had reached a multi-grain topology.
- **The fence had to move with it.** Joining the fact's table converts a bind error into a returned number, so `fan_trap::check_referenced_fact_fan_traps` rejects a fact on a table that *fans* relative to its member's — the same condition already applied to a queried dimension and to a `where_clause` member, and the reason this was filed rather than fixed in the pass that found it. Without the fence a fact on a child table would have been silently joined into a base-anchored aggregate and inflated it, trading a loud failure for a silent wrong number.
- **Two sibling gaps in the same class, found in review of #200 and fixed with it.** A *derived* metric's own expression names metrics rather than facts, so the per-grain `group_fact_tables` (since folded into `per_grain::anchor_needs`) — which scanned only the group's own metric expressions — missed facts reached through the base metrics inlined into it, reintroducing the defect inside the grain CTE (Copilot). Probing the neighbourhood then turned up the facts-path equivalent: a *queried* fact whose expression chains to a fact on a third table was inlined without that table being joined, since `fact_source_tables` carries only each queried fact's own declared table. Both now walk the chain.

### 52. ✅ A raw cross-table column reference is accepted at CREATE and fails as a DuckDB binder error at query time (PAR-3) — RESOLVED 2026-08-05

- **Origin:** code review 2026-08-03 (`_notes/code-review-2026-08-03.md`, PAR-3). Filed MEDIUM as "cross-table column references in member expressions unsupported and undocumented".
- **The review's premise was half wrong, checked against current Snowflake docs.** PAR-3 assumed "Snowflake permits expressions to reference related logical tables". Snowflake's validation rules say the opposite for raw columns: "Expressions cannot refer to base table columns from other tables or expressions from unrelated logical tables." So the *rule* is at parity — a member expression is scoped to its own logical table in both systems. What diverges is enforcement: Snowflake rejects the definition at CREATE, this extension accepts it.
- **Symptom:** `o.margin AS o.amount - c.discount` expands to `SUM(o.amount - c.discount) FROM "orders" AS "o"` with no join for `c`, so DuckDB reports an unknown alias when the member is queried. Never a wrong number — the alias is qualified, so the query cannot bind — but the error names DuckDB's missing alias instead of the semantic-layer rule that was broken, and it arrives at query time rather than at CREATE.

For every fact, dimension and metric expression it walks the **qualified** reference chains and rejects one whose qualifier names a declared table that is neither the member's own nor the qualifier of a declared fact or metric of that name. The message names the rule and the supported alternative — define a FACT on the other table — rather than an alias.
- **Deliberately conservative in one direction:** a qualifier matching no declared table is left alone (a struct path root, a bound parameter, a plain typo). Rejecting those would turn every expression this layer cannot fully model into a CREATE failure; the check fires only where the *semantic* model can say the reference is out of scope. Function-call heads and string literals never reach it — `expr_tokens::scan_references` excludes both, which is what keeps `SUM(c.udf(x))` and `'c.discount is not a ref'` out of the reject set.
- **Coverage:** ten `graph::member_refs::tests` — the rejection for each member kind, the three legal forms (cross-table fact, derived metric over metrics on other tables, same-table fact in a dimension per #54), the base-table case for a member with no `source_table`, and the four false-positive guards (unknown qualifier, struct path, qualified call, string literal), plus case-insensitive and quoted qualifier matching. `member_reference_scoping.test` covers CREATE-time rejection and both controls end to end.

It expands a request for the members and runs the expanded SQL with `LIMIT 0`; the reported type is the one `semantic_view()` *declares* for that column (`query::wire::declared_type_name`, a mirror of the C++ bind's `sv_logical_type_from_c_type_id`, plus a `DESCRIBE` for the parameters of a DECIMAL / LIST column), so `data_type` always equals `typeof()` of the member's column in a query — including the query path's own normalisation (`SUM` over an integer is BIGINT, not DuckDB's HUGEINT; ENUM / STRUCT / MAP are VARCHAR). A batch that does not expand or bind (a fan trap between two members, a semi-additive metric that cannot share a query with a derived one, a dropped source) falls back to one probe per member of that kind. A window metric is probed alone with the dimensions its `PARTITION BY` / `ORDER BY` requires (`expand::window_required_dimensions`). Measured on a debug build, `SHOW SEMANTIC METRICS` across 100 views × 10 metrics took 179 ms (26 ms before), and 396 ms with every source table dropped (the all-fallback worst case); a single-view SHOW / DESCRIBE is unchanged at ~7 ms. Linear in the member count, as the cross-view form necessarily is: its `IN SCHEMA` / `LIKE` filters are applied after the table function returns, so they do not narrow the probe set.
  - **Cancellation** (PR #248 review). The probes run on the bind's own `Connection(*context.db)`, whose interrupt flag a cancel of the caller never sets, so pre-fix a cancelled cross-view SHOW kept probing every view and a probe over a slow-binding source ran to completion; INTERRUPT surfaced only afterwards. Every varchar bind helper in `cpp/src/shim.cpp` now holds an `SvBindCancellationScope` for the dispatcher call: it exposes the caller's flag to Rust (`sv_bind_caller_interrupted`), which checks it before each probe and stops typing with `member_types::Interrupted`; a watcher thread forwards the flag into the probe connection, so a probe already binding stops at the engine's own poll points (glob expansion, optimiser passes); a probe failing with `DUCKDB_ERROR_INTERRUPT` is classified as a cancellation rather than an untypable member; and a cancelled caller is raised as a bare `InterruptException`, not the `"<fn> failed: ..."` binder wrapper. Cost: one short-lived thread per read-side bind.
  - **A member that cannot be typed** — its source table or column was dropped or renamed, or its expression no longer binds — reports an empty `data_type` (or a legacy pre-#68 definition's declared `output_type`). SHOW / DESCRIBE never fail on that account; querying the member still raises the binder error. The column stays VARCHAR and empty rather than NULL, matching how the other optional SHOW columns (`comment`) report absence.
  - **PRIVATE members** are typed by probing a copy of the definition in which every member is PUBLIC; the copy is never stored or queried.
  - **Role-played members** (on, or reached only through, a table that two or more relationships from one source point at) are rejected as ambiguous when probed without a role. They are retried on a copy that keeps only the first-declared relationship of each such pair; the type does not depend on the role. The copy is used for typing only; every real query still goes through the role-playing checks.
- **Coverage:** `test/sql/member_data_type.test` (22 cases, each confirmed red individually against the pre-fix build: dimension, quoted mixed-case dimension on a joined table, LIST, COUNT / AVG / SUM / DECIMAL SUM / MAX, derived, window, semi-additive, PRIVATE, facts, cross-view SHOW, DESCRIBE, SHOW COLUMNS, SHOW DIMENSIONS FOR METRIC, a column retyped after CREATE, a dropped column, a dropped table, a non-default schema, ENUM / STRUCT / HUGEINT, a role-played dimension / fact / metric), with `typeof()` controls pinning that each reported type is what `semantic_view()` returns. `src/query/member_types.rs` unit tests cover the same shapes plus the declared-type map against `typeof()` for every C-API type id, the one-probe-per-kind cost guard, the per-member fallback and the role-played fallback. `tests/member_type_proptest.rs` randomizes it against a `typeof()` oracle that never goes through expansion, and against the type each member has in a random co-queried request, with a drop axis. ### 50. ✅ A root-grain component of a derived metric vanished from its grain set, and the per-grain planner anchored it at another table (EXP-11) — RESOLVED 2026-08-05

- **Origin:** code review 2026-08-03 (`_notes/code-review-2026-08-03.md`, EXP-11). Filed MEDIUM, in the EXP-8 class.
- **Was:** EXP-8 established that a metric with no `source_table` and no base-metric references sits at the **root** grain, and taught the fence to substitute the root for an *entirely empty* grain set. `collect_derived_metric_source_tables` contributes no table for such a metric, so the substitution only ever fired when nothing else contributed one either. A derived metric depending on both a source-less aggregate (root grain) and a base metric on a fanning parent table therefore reported a grain set of `{parent}`: non-empty, so no substitution, and the root component simply disappeared.
  - **Symptom 1 (single grain).** `plan()` saw one grain, took its fast path, and anchored the metric's **whole** resolved expression — both aggregates — at the parent, then ran the fence in per-grain mode, which skips the EXP-1 root-grain and EXP-2 within-metric checks. Emitted `SELECT (SUM(c.balance)) - (SUM(amount)) FROM "customers" AS "c"`: silently wrong if `customers` has an `amount` column, a confusing binder error if not. v0.11.0 raised `RootGrainFanTrap` for the same query.
  - **Symptom 2 (multi-grain).** With two real grains the planner reached `decompose`, which skips every source-less dependency as "derived, inlined by the reference walk". For an aggregate one that spliced the raw `SUM(amount)` into the **outer** SELECT over the grain CTEs, where its table is not in scope.
- **Resolution:** the empty→root substitution is now made per *component*. The dependency walk reports a `DerivedMetricGrain { tables, at_root }` — `at_root` set when it passes a metric with no `source_table` whose expression aggregates — and `MetricGrain::anchored(root)` supplies the caller's root alias for it. The flag is carried separately rather than pushed into the table list because the walk sees only the metric list; the root alias belongs to `GrainGraph`. All five fence sites and the planner now share `anchored`, replacing five hand-written `if tables.is_empty() { push(root) }` copies of the EXP-8 rule. `decompose` declines outright on a source-less aggregate dependency: it needs a component CTE of its own, and there is no table to anchor one at.
- **A window metric is exempt from `at_root`,** and this is the one subtlety worth stating: its expression is `<fn>(<inner>) OVER (…)`, an aggregate over a metric *reference*, evaluated on the inner metric's pre-aggregated row set rather than any table of its own. `metric_grain` already adds the inner metric's grain separately, so counting the outer window function would put every window metric at the root grain **on top of** its real one — a window metric over a child-table aggregate would then fan-trap against its own dimension. Caught by two pre-existing `tests_count_star_rewrite` tests before the exemption was added.
- **Honest scope: this restores an error, it does not compute the answer.** These queries now decline to the base-anchored path and raise `RootGrainFanTrap` — the v0.11.0 answer, and the correct one until the root component can be given a CTE of its own. Giving it one is a real fix and is **not** done here: the per-grain emitter anchors each group at a named table, and a root-grain component would need a group anchored at `GrainGraph::root` with the other components joined to it. That is TECH-DEBT #35/#36 territory (per-grain emission) rather than a fence change, and no DDL-reachable query needs it — see reachability below.
  - **The gap is one qualification wide, and that is the workaround.** Give the same metric a `source_table` — what DDL requires anyway, `o.root_total AS SUM(amount)` — and `decompose` treats it as an ordinary component: verified by probe, the mixed metric emits two grain CTEs (`SUM(c.balance)` over `customers`, `SUM(o.amount)` over `orders`) and returns a number. So the unanswered case is exactly the one whose metric never said where it aggregates, which is also why building the missing anchor was not worth doing speculatively. `derived_metric_with_rootless_aggregate_component_errors` pins the error, and its comment says why the error is the intended answer rather than a placeholder.
- **Reachability — why MEDIUM and not HIGH.** Current DDL cannot declare a source-less *aggregate* metric: `alias.name` qualification is mandatory and `validate_derived_metrics` rejects an aggregate in an unqualified entry. The shape exists only in legacy stored catalog rows and in constructed definitions — exactly the population EXP-8 was added to protect, which is why leaving the planner and the fence inconsistent about it was not acceptable.
- **Coverage:** three `expand`-level tests in `tests_per_grain.rs` (`derived_metric_with_rootless_aggregate_component_errors`, `multi_grain_derived_metric_with_rootless_aggregate_component_errors`, and the control `rootless_aggregate_mixed_with_root_table_component_stays_at_root`, which pins that a metric whose components are *all* at the root still emits `(COUNT(*)) + (SUM(amount)) FROM "orders" AS "o"` with no per-grain CTEs — a fix that over-declined would fail it), plus three unit tests on the walk itself in `facts.rs` (`test_collect_grain_rootless_aggregate_dependency_reports_at_root`, `test_collect_grain_plain_derived_metric_is_not_at_root`, `test_collect_grain_window_metric_outer_aggregate_is_not_at_root`).
- **Each case confirmed red individually.** The two symptom tests were written first and watched fail against the pre-fix code, each printing the exact wrong SQL quoted above. The three unit tests were then mutation-verified one at a time — dropping the `at_root` assignment, dropping the window exemption, and dropping the aggregate check each turned exactly **one** of the three red and left the other two green, so none of them passes vacuously.
- **No numeric-oracle work, and why — checked rather than assumed.** No DDL-reachable query changes: `at_root` can only be set by a metric DDL refuses to create, and for every other metric `anchored()` returns exactly what the five hand-written substitutions returned. The two sites that now call `anchored()` where they previously read the raw table list (`snapshot_cte_anchor`, `anchored_window_anchor`) both matched on a single-element slice and returned `None` on an empty grain; the substituted `[root]` now matches and is immediately rejected by their existing `if anchor == root { return None }`, so the outcome is unchanged there too. The five numeric harnesses build their definitions through DDL, so they cannot generate the shape at all — and for it there is no number to oracle, since the correct behaviour is an error.

### 47. ✅ `where_clause` bypassed PRIVATE and never resolved qualified member references (EXP-13 / EXP-14) — RESOLVED 2026-08-04

- **Origin:** code review 2026-08-03 (`_notes/code-review-2026-08-03.md`, EXP-13, EXP-14). Both filed LOW; EXP-14 is materially worse than filed — see below.
- **EXP-13 was:** `resolve_where_clause` built its member lookup from *all* of `def.dimensions` / `def.facts` with no `AccessModifier` check, so a PRIVATE fact that `resolve_names` refuses to let you select could still be named in a predicate — and its values probed by varying the filter and watching the result move. The queried-member path has enforced PRIVATE since Phase 43; the predicate path did not. Only facts are affected: `PRIVATE` on a dimension is rejected at CREATE (`body_parser::entries`), which is why `sql_gen`'s `Resolvable` impl carries `unreachable!("dimensions cannot be private")`. (The 2026-08-03 review filed that rejection as an undocumented divergence, PAR-4. Checked against current Snowflake docs on 2026-08-05 it is **not** a divergence: "You cannot mark a dimension as private. Dimensions are always public." The comparison table now states the parity instead of implying a narrowing.)
- **EXP-14 was:** `scan_references` keys a dotted chain by the whole chain (`o.order_date`), but the member lookup was keyed by bare name only. A qualified reference therefore matched **nothing**.
- **EXP-14's real severity — a fan-trap fence bypass, not just an unsubstituted reference.** The finding predicted a raw column that "fails loud at bind". It does worse. `ResolvedWhere::source_tables` is what feeds the predicate's tables into the fan-out check, and it is populated *only* for references that resolve. An unresolved qualified reference therefore removes its member from the fence's input entirely, so a predicate that reaches a fanning grain is silently accepted. Caught by the extended oracle, whose minimal counterexample is unambiguous:

  ```sql
  SELECT sum(u.uw) AS "su"
  FROM "u" AS "u"
  WHERE ((u.ucat) <= 1 AND t.ftd)
  ```

  `t.ftd` names a filter member on `t`. Pre-fix it resolved to nothing, `t` never entered `source_tables`, the fence never learned the predicate reached `t`, and the query was **accepted** with `t` not even joined. This is the same class as EXP-10, which was rated HIGH. It happens to bind-fail here only because `t.ftd` is not a real column; where a member name coincides with a real column on its own table, it binds and returns a wrong number with no error.
- **Resolution:** every member is keyed both bare and by its own `source_table.name`, mirroring `expand::facts::insert_fact_keys` and the dotted-reference handling at the NA-dim and window sites (#28/#30). Keying by the member's **own** table is what keeps a *foreign* qualifier (`c.order_date`) an ordinary column per E-3. Metrics are keyed both ways too, so `o.revenue > 5` now raises `WhereClauseReferencesMetric` instead of slipping through. PRIVATE facts are deliberately kept *out* of the lookup and recorded separately, so a reference to one raises `PrivateFact` rather than falling through to "unknown reference" — which would have left it in the SQL as a raw column and leaked the very member PRIVATE withholds.
- **Coverage:** seven unit tests, each confirmed red before the fix, plus controls (`a_public_fact_still_resolves_in_the_predicate`, `a_foreign_qualified_reference_is_left_as_a_raw_column` — the latter guarding against over-eager substitution). Randomized: `multi_hop_join_proptest`'s predicate generator now varies each member reference between bare and `<table>.<name>` spellings, with the oracle rendering unchanged so the comparison stays differential. Verified by reverting only the fix and watching the harness go red on the case above. `generator_reaches_both_where_clause_branches` gained an assertion that both spellings occur, so the flag cannot be silently pinned to `false` — the `where_clause: None` mistake (PBT-6) one level down.
- **Not covered:** `differential_proptest` cannot host this — its members carry `source_table: None`, so a qualified spelling does not exist there. Left alone rather than restructured.

### 42. ✅ `semantic_view()` ignored query interrupts — cancellation never reached the inner query — RESOLVED 2026-08-04

- **Cited as "#39" in its own commit.** `2d7d9cc` ("fix(query): make `semantic_view()` observe query interrupts (TECH-DEBT #39) (#190)") names the wrong entry — #39 is the fan-trap / `NON ADDITIVE BY` item (EXP-9), unrelated. The interrupt work is this entry, #42. Noted because the commit subject is immutable and a `grep` from the history otherwise lands on the wrong section.
- **Origin:** external bug report, found while implementing the async query surface of a downstream project (Semolina v0.7) whose "a cancelled query must be cancelled at the warehouse, not merely abandoned by the client" requirement could not be demonstrated against semantic views. Not caught by the 2026-08-03 code review, which did not look at the C++ execution shim's cancellation behaviour (`grep -niE "interrupt|cancel"` over that review returns nothing).
- **Was:** `duckdb_interrupt()` — and therefore ADBC's `adbc_cancel()`, an interactive Ctrl-C, and any framework-level timeout built on either — had no effect on a query running through `semantic_view()`. The query ran to full completion and the interrupt surfaced only afterwards. Measured on a ~3.9s aggregate cancelled at 0.4s: 3.9s to stop via `semantic_view()`, 0.41s for the identical aggregate as hand-written SQL.
- **Cause:** DuckDB's `interrupted` flag is a per-`ClientContext` atomic, and `sv_semantic_view_init_global` ran the expanded SQL on a **fresh** `Connection(*context.db)` — a brand-new `ClientContext`. The flag was set on the caller's context and read on the inner one; nothing bridged them. Compounding it, there was no yield point: `Connection::Query` blocks until the inner query finishes, and the outer executor's own interrupt checks live in `PipelineExecutor::Execute`, which does not run until `init_global` returns. That is exactly the observed shape — full runtime, *then* INTERRUPT.
- **Resolution:** `sv_query_interruptible` (`cpp/src/shim.cpp`) unrolls the loop `Connection::Query` runs internally (`PendingQueryResult::ExecuteInternal`) into `PendingQuery` + `ExecuteTask()`, giving a poll point between tasks. The outer `ClientContext &` that `init_global` already receives is checked there; on a cancel the flag is forwarded to the inner connection via `Connection::Interrupt()` and the loop keeps draining, so the inner executor's tasks wind down before the `Connection` leaves scope, and only then is a **bare** `InterruptException` thrown.
  - **Bare is load-bearing.** ADBC maps a failure to `ADBC_STATUS_CANCELLED` only on an exact string match against `InterruptException::INTERRUPT_MESSAGE` (`"Interrupted!"`). The interrupt branch is deliberately taken inside the helper, *ahead* of the `InvalidInputException("semantic_view: SQL execution failed: …")` wrap in `init_global`, or a cancelled query would surface as `ADBC_STATUS_INTERNAL`.
  - Everything else matches `Connection::Query`, including returning an error-carrying result rather than throwing, so `init_global`'s existing `HasError()` handling and the `semantic_view: SQL execution failed: …` wording are unchanged. That wording turned out to have **no** test pinning it — the refactor moves where the error is produced, so `semantic_view_runtime_error.test` was added to pin it. It is a guard rather than a capability (it passes on both sides of this change by design), and non-vacuity was verified by perturbing each of its three assertions in turn and confirming each goes red independently — the runner halts a file at its first failure, so one run could not have proven all three. One behavioural difference is accepted: a *multi*-statement string would now be rejected (`Cannot prepare multiple statements at once!`) rather than executed. `execution_sql` is always a single generated `SELECT`.
  - Guarded by `test/integration/test_query_interrupt.py` (`just test-interrupt`, wired into `test-integration`). It asserts **timing** and **error shape** separately, because the pre-fix build satisfies the latter — the outer pipeline does eventually raise a bare INTERRUPT, just 3.9s too late — so a shape-only assertion would have passed against the bug. A plain-SQL twin runs first through the identical harness as a control: it aborts early on every build, so a control failure means the harness is broken rather than the feature. Confirmed red against the pre-fix build with every other assertion in the file passing, so the one failure is the defect and not a broken fixture.
  - **Timing tolerance recalibrated 2026-08-10, after the assertion false-positived during v0.12.0 release prep.** It was `FIRE_AT_S + max(1.0, 0.30 * baseline)` — a budget for the abort *delay*. But that delay does not scale with the baseline: it is bounded by how long one `ExecuteTask()` chunk takes, which is a property of the calibrated md5 depth, and was measured at 0.65–1.72s across baselines from 3.3s to 4.8s on one machine. The allowance sat inside that range, so the verdict turned on where calibration happened to land; under full-suite load a build that aborted at 46% of baseline (2.21s of 4.78s) was failed. Three consecutive fresh runs afterwards would each have failed the old formula while aborting correctly. The tolerance is now a fraction of the uninterrupted baseline (`max(FIRE_AT_S + MIN_ABORT_SLACK_S, ABORT_FRACTION * baseline)`, 0.6 and a 1.5s floor), which is what the assertion is actually about: the regression makes the query run to completion, so "stopped partway" and "stopped at ~baseline" are the two outcomes to separate, and a fraction of the baseline sits between them on any machine.
  - **The floor made a vacuous pass reachable, so that is now asserted against.** On a machine fast enough for the floor to dominate, the limit can climb to the baseline itself — at which point every assertion below passes for a build that never observed the interrupt, which is precisely the defect this entry exists to guard. A precondition now requires the limit to be at most 75% of the **measured** baseline (not a calculation over the constants) and hard-fails with a pointer to `TARGET_BASELINE_S` otherwise. Re-verified in both directions on 2026-08-10: the recalibrated limit passes the current build with ~2× headroom, and against a simulated pre-fix build — the interrupt fired on a decoy connection, so the flag lands on a `ClientContext` the inner query never polls — the timing assertion goes red (6.54s vs a 2.89s limit) with the vacuity precondition passing, confirming the limit was still discriminating rather than the test having become inert.
- **Residual gaps, stated rather than hidden:**
  - **Bind-time probes stay uninterruptible.** Every `semantic_view()` bind runs a `LIMIT 0` type-inference probe (`src/query/table_function.rs:241`, plus the DECIMAL/LIST `sv_resolve_output_logical_types` probe in the shim). Deliberately left alone: DuckDB's optimizer short-circuits `LIMIT 0` before touching any data — measured at **4ms** against an aggregate whose full run takes **7.9s** — so there is no window worth cancelling in, and the Rust-side probe would need the outer `ClientContext` plumbed across the FFI boundary to reach. Revisit only if that probe ever stops being `LIMIT 0`.
  - **`WaitForTask()` on a `BLOCKED` inner query is not itself a poll point.** `BLOCKED` is an async-I/O state (httpfs and friends); for local aggregates it does not arise. The wait is bounded — `Executor::WAIT_TIME` is 20ms — so it costs at most one such window of latency per poll rather than blocking indefinitely.
- **Not fixed here — the structurally correct shape is `bind_replace`.** DuckDB's own `query()` / `query_table()` parse generated SQL into a `TableRef` that the **outer** binder plans inline, eliminating the nested connection entirely. That would fix cancellation as a side effect, and additionally the full-result materialization (the whole result is buffered before the first scan), the hardcoded `MaxThreads` of 1, and the lost filter/projection pushdown. It also removes the bind-time schema declaration and both `LIMIT 0` probes, requires relaxing the `bind`/`exec`/init-XOR guard, and changes error-message text that sqllogictest matchers pin byte-identically — so it is a separate, larger item, deliberately not coupled to this fix.

### 37. ✅ RESOLVED (v0.12.0) — `JoinTree`'s parent map was degenerate under fan-in onto the base table

- **Origin:** discovered in v0.12.0 (Phase 69) while giving the fan-trap fence a correct path derivation. Recorded rather than fixed, to keep that milestone's diff to the per-grain change plus the fence gap it exposed.
- **Was:** `JoinTree::from_graph` took each node's parent as `graph.reverse[node].first()` — the FIRST table that references it. With fan-in onto the base table (two children of one parent, e.g. `line_items` and `shipments` both referencing the base table `orders`) `reverse["orders"]` has two entries, so the base table itself was given a "parent" (the first-declared child) and chains ran *through* the root and out the far branch. Fan-in onto a non-root node is not affected: `check_no_diamonds` rejects it at define time as an ambiguous join diamond, so root fan-in is the only shape that reached this code.
- **Impact:** a **false rejection**, not a wrong answer. A fact query selecting a fact on `shipments` with a dimension on `customers` (`s → o → c`, all many-to-one) was rejected with `FactPathViolation` though the path is safe, and the `extension`-gated `SHOW SEMANTIC DIMENSIONS … FOR METRIC` filter hid the same dimensions for the same reason.
- **Resolution:** two changes, because the parent map alone was not sufficient.
  1. `JoinTree::from_graph` now derives the map by BFS from the base table over the undirected edges — the same walk `expand::join_resolver::build_tree_parents` performs — so each node's parent is its neighbour *toward* the base table. Nodes with no path to the declared base table keep the legacy reverse-edge parent, preserving degenerate definitions. This fixes the `SHOW … FOR METRIC` filter, which pairs the tree with its own cardinality map and so already checked fan-out direction.
  2. `validate_fact_table_path` no longer asks about ancestry at all. Correctly rooting the tree makes the base table an ancestor of *every* alias, including the fan-in siblings it can only reach by walking a many-to-one edge backwards — so an ancestry test would have swapped the old false rejection for a false acceptance (silently row-multiplied fact output). It now walks the undirected path and rejects the pair unless it is traversable in at least one direction without crossing a many-to-one edge backwards, reusing `find_path` + `fanning_edge_on_path`.
- **Coverage:** `graph::join_tree::tests::from_graph_roots_the_tree_at_the_base_table_under_fan_in`, `expand::tests_fact_query::{fact_with_dimension_across_fan_in_is_allowed, fact_reaches_a_multi_hop_chain_across_fan_in, fact_across_fan_in_siblings_still_violates}`, and `test/sql/fan_in_fact_path.test` (both consumers end-to-end, including the over-widening guard).
- **Left behind:** `JoinTree`'s only remaining production consumer is the `extension`-gated SHOW filter, so it is dead code in the default build and carries `cfg_attr(not(feature = "extension"), allow(dead_code))` accordingly.
